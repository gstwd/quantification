# 系统架构问题分析

> 分析日期：2026-08-21
> 范围：后端（FastAPI + PostgreSQL）、前端（Vue 3）、数据摄取/调度、策略引擎、AI 因子链路
>
> 结论先行：系统分层合理、策略引擎组件化设计是亮点，但存在并发模型、任务执行上下文分裂、实时查询路径重计算、数据层索引不匹配等结构性问题，另有未接线的并行架构和文档漂移。

---

## 二、高优先级问题

### P1. 全同步栈 + 外部 API 调用阻塞请求线程

**现状**

后端完全同步：所有路由均为 sync 函数，运行在 FastAPI 默认的 40 线程线程池中；外部数据抓取通过 `urlopen` / AkShare 同步阻塞执行。虽然 `IngestService` 使用 per-resource `threading.Lock` 实现了读穿缓存（见 `apps/api/src/quant_etf_api/services/ingest_service.py` 的 `_fetch_locks`），但该锁只串行化"首次抓取"，不解决线程占用问题。

**风险**

- 冷启动或多个数据源同时失联时，数十个请求线程同时卡在网络等待，线程池耗尽后 API 整体超时。
- 同步阻塞在 GIL 下还会加剧 CPU 型因子计算的延迟。

**建议方向**

- 外部数据抓取迁移到独立 worker 进程/任务队列（如 Celery、RQ 或独立 ingest 服务），HTTP 层只负责触发和查询状态。
- 短期内可先增大线程池并限制外部调用并发（信号量），但属于治标。

**处理结果（2026-08-24）**

- GET 读穿透缓存不再在请求线程同步抓取外部 API：`IngestService` 的 5 个读穿方法（ETF 日线/份额、指数日线/估值、宏观）未命中时入队 `data_fill` 后台任务并立即返回空列表。
- 新增基于 PostgreSQL 的持久化任务队列 `background_job`（迁移 0023）+ 固定 worker 线程池（`apps/api/src/quant_etf_api/infra/job_queue/`），外部抓取统一在 worker 中执行，请求线程不再被上游网络拖死。
- 短期"增大线程池 + 信号量限流"方案不再需要。

---

### P2. 后台任务执行上下文分裂为 4 条路径

**现状**

名义上所有后台任务共用统一 executor（`apps/api/src/quant_etf_api/api/executor.py`，`ThreadPoolExecutor(max_workers=3)`），实际存在四种互不统一的执行方式：

1. 回测、摄取、策略运行走共享线程池；
2. 每日数据调度与 AI 调度是裸 `threading.Thread`（`apps/api/src/quant_etf_api/infra/scheduler/__init__.py`）；
3. `startup_fill`、`warm-calendar` 由 `main.py` 自行创建 daemon 线程；
4. 策略对比回测在 `run_comparison` 内部再嵌套一个 `ThreadPoolExecutor(max_workers=2)`（`apps/api/src/quant_etf_api/services/backtest_service.py`）。

**后果**

- 一次对比回测占 1（外层）+ 2（内层）= 3 个 worker，恰好占满全局线程池，饿死其他回测任务。
- 线程生命周期不统一，shutdown 时 `join(timeout=30)` 超时后 daemon 线程被进程强杀，可能中断进行中的 DB 写入。
- 任务无持久化队列，进程重启只能"标记失败"兜底，没有恢复重跑机制。

**建议方向**

- 统一为单一任务队列 + 固定 worker 池，所有后台任务（含调度触发的）走同一入口。
- 去除嵌套线程池；对比回测的两个子任务也应作为队列中的独立任务调度。
- 任务队列持久化，支持崩溃恢复与重试。

**处理结果（2026-08-24）**

- 已删除 `api/executor.py`；所有后台任务（摄取、因子计算、回测、对比回测、AI 分析、启动补全、交易日历预热、GET 补数）统一入队 `background_job`，由 `JOB_HANDLERS` 分发表 + 固定 worker 池执行。
- 数据摄取与 AI 调度器退化为纯定时器（只入队不执行）；`startup_fill` / `warm_calendar` 由 `main.py` lifespan 直接入队。
- 对比回测改为 fan-in：`comparison` 处理器入队两个 `backtest` 子任务后立即返回，子任务完成后由 `finalize_comparison_if_ready` 汇总，嵌套 `ThreadPoolExecutor` 已删除。
- 队列持久化于 PostgreSQL：进程重启后 pending 任务继续执行，running 任务由 `recover_stuck_jobs` 标记失败；`data_fill` 支持 `max_attempts=2` 重试。

### P3. 实时查询路径含重计算与写路径

**现状**

`GET /strategies/{id}/allocation` 与星标摘要等"查询"接口在因子缺失时会同步触发全量因子重算并 `commit`（见 `apps/api/src/quant_etf_api/engine/context_builder.py` 的 `_build_live` 按需补算分支）。`get_starred_summary` 对每个星标策略串行跑完整管线，且每次重新查库构建上下文（`apps/api/src/quant_etf_api/services/strategy_service.py`）。

**后果**

- 写操作（因子计算 + commit）出现在 GET 链路中，且无并发控制，并发请求会重复计算同一批因子。
- 策略数量增多时星标摘要接口线性变慢。
- 信号结果已持久化到 `index_signal`，查询端却不读缓存，每次都全量重算。

**建议方向**

- 因子缺失时改为异步补算（触发后台任务），GET 返回"数据未就绪"或回退到已有最近数据。
- 星标摘要共享同一份上下文（一次性加载行情/因子，多个策略复用）。
- 实时分配接口增加结果缓存（按策略 + 交易日）。

**处理结果（2026-08-24）**

- `ContextBuilder._build_live` 已删除按需 `FactorService.compute_and_store() + commit` 分支：保留三层缺失检测，检测到缺失时入队 `factor_computation`（按交易日去重），GET 链路不再产生写操作。
- 星标摘要共享上下文、`index_signal` 结果缓存仍为后续优化项，不在本次范围。

### P4. 配置驱动引擎的校验缺口

**现状**

`validate_config` 为纯静态校验（`apps/api/src/quant_etf_api/services/strategy_config_service.py`），只校验操作符、权重、portfolio 方法等结构字段，**不校验引用的因子 ID 是否真实存在于注册表/数据库**。

**后果**

- 因子名拼写错误时配置校验仍通过，运行时被 `missing_factor_strategy="ignore"` 静默跳过，最终产出空仓位/错误信号。
- 违背"配置驱动、无需代码、快速失败"的设计初衷；错误在交易决策层静默暴露，排查成本高。

**建议方向**

- 校验时注入 `FactorRegistry` 或查询 `factor_definition` 表，未知因子 ID 直接报错。
- 增加配置版本字段，引擎配置模型变更时做迁移兼容检测。

## 三、中优先级问题

### P5. 数据库索引与热点查询模式不匹配

**现状**

大表唯一约束均以 `trade_date` 为前导列：

- `uq_etf_daily_bar (trade_date, etf_code)`
- `uq_index_daily_bar (trade_date, index_code)`
- `uq_index_valuation (trade_date, index_code)`
- `uq_index_factor_value (trade_date, index_code, factor_id, strategy_id)`

（见 `apps/api/src/quant_etf_api/infra/db/models/core.py`）

**后果**

- 热点查询是代码导向的范围扫描（`WHERE index_code = ? AND trade_date BETWEEN ...`），前导列为 `trade_date` 的索引无法高效服务。
- 因子导向查询（IC/IR 评估、因子详情页按 `factor_id` 查询）同样受限。
- 数据量增长（ETF × 约 250 交易日/年 × 因子数）后查询明显退化。

**建议方向**

- 为 `(etf_code, trade_date)`、`(index_code, trade_date)` 增加二级索引。
- 为 `index_factor_value` 增加 `(factor_id, trade_date)` 索引以服务因子评估查询。
- 通过迁移（alembic revision）添加，并验证执行计划。

---

### P6. 两套数据访问架构并存，新架构未接线

**现状**

`apps/api/src/quant_etf_api/infra/data_sources/` 包含完整的多源管理架构：`DataSourceManager`、`CircuitBreaker`、4 个 adapter、2 个 placeholder。但实际摄取链路仍走旧的 `infra/clients/` 目录；`data_source_priority`、`circuit_breaker_*` 等配置项未生效。

**后果**

- 死代码挂在代码库中，增加维护面与认知成本。
- 读者可能误以为系统具备多源故障切换能力。

**建议方向**

- 二选一：将 `IngestService` 切换到 `DataSourceManager` 并删除旧 clients；或删除 `infra/data_sources/` 及对应配置。
- 若保留，则必须让配置项真实生效并补充集成测试。

---

### P7. 事务边界与写入粒度不一致

**现状**

- 数据摄取：`_process_etf_ingest_batch` 对每个 ETF 独立 commit（`apps/api/src/quant_etf_api/services/ingest_service.py`），整个 ingest 无整体事务边界；并发被锁挡住时把运行记录标记为 `success` 而非 `skipped`，状态语义不准。
- 回测：所有每日结果在内存累积后最后一次性提交，长区间回测事务大，中途失败全部回滚，无部分结果可查看（`progress` 仅更新数字）。

**建议方向**

- 摄取失败时记录为 `failed` 或 `skipped` 语义；逐条 commit 可保留，但需明确"部分成功"的展示。
- 回测可按区间分段提交（如按年度 checkpoint），失败时保留已完成区间结果。

---

### P8. AI 分析链路串行且阻塞调度线程

**现状**

`analyze_batch` 串行逐批调用 LLM（`apps/api/src/quant_etf_api/ai_factors/analysis/sentiment.py`）：最多 150 条、20 条/批，即最多 8 次 LLM 调用，每次 60s 超时 + 重试，全部运行在 AI 调度器单线程中。

**后果**

- 23:30 启动的 AI 分析可能拖到凌晨。
- 进程退出时 `join(timeout=30)` 超时后线程被强杀，可能中断分析链路。

**建议方向**

- LLM 批处理并行化（受 API 限流约束，控制并发数）。
- AI 分析走独立 worker/队列，与调度线程解耦。

---

### P9. 前端轮询分散、生命周期不统一

**现状**

2 秒轮询散落在 store 和页面中。`RunsPage` 在 `onUnmounted` 正确清理定时器（`apps/web/src/pages/RunsPage.vue`），但 `backtests` store 的 `pollUntilDone` 与组件生命周期无关（`apps/web/src/stores/backtests.ts`），用户切走页面后轮询仍持续到任务结束。

**后果**

- 无效请求占用后端线程池和数据库连接。
- 轮询逻辑重复实现，维护成本高。

**建议方向**

- 抽取统一的轮询 composable，自动绑定组件生命周期。
- 长任务状态改为 WebSocket/SSE 推送或服务端缓存 + 页面级单一轮询。

## 五、其他值得注意的小问题

- `ContextBuilder._build_live` 加载估值时未按 `index_codes` 过滤，全量加载后内存过滤（`apps/api/src/quant_etf_api/engine/context_builder.py`）。

## 六、建议处理顺序

若按"稳定服务、多人协作、数据量增长"方向演进，建议按以下顺序处理：

1. **收敛任务执行模型**（P2）：统一队列 + worker，去除嵌套线程池。
2. **移出实时查询链路的写路径**（P3）：因子补算异步化，结果缓存。
3. **补齐索引**（P5）：code-led 与 factor-led 查询索引。
4. **接入或删除 `infra/data_sources`**（P6）。
5. **校验兜底因子 ID**（P4）：注册表校验，快速失败。
6. 依次处理 P1、P7、P8、P9、P10。

> 若定位为个人/小团队研究工具，当前架构可用，优先处理 P3 与 P4 即可显著降低"策略静默失效"与"接口不可用"两大风险。

> 更新：第 1、2 项（P2、P3）与 P1 已于 2026-08-24 一并实施完成，见对应章节"处理结果"；剩余建议顺序调整为 P4 → P5 → P6 → P7 → P8 → P9 → P10。

## 七、业务分层问题分析（数据层 / 因子层 / 策略层 / 回测层）

> 本部分聚焦四层各自的独立逻辑与层间协作逻辑，作为第六部分问题的补充视角。
>
> 总体结论：四层内部基本自洽（因子层的 Protocol + 注册表抽象最好），真正的问题集中在**职责归属**与**层间协作契约**——存在依赖方向倒置、三处重复编排、因子契约传递降维等问题。

### 7.1 分层现状总览

```
HTTP → api/routers → services → engine（编排器 + 组件模块）→ factors（FactorProvider/FactorService）
                                      ↓                        ↓
                               domain（纯业务规则）      infra（db / clients / scheduler）
```

层间协作的主要载体：

- **EngineContext**：策略引擎执行上下文，承载 universe、asset_factors、market_factors、extra。
- **FactorProvider**：桥接因子层与引擎层，实时从 DB 加载、回测批量预计算。
- **ContextBuilder**：统一构建实时/回测上下文。
- **StrategyConfig**：配置驱动引擎的 JSON 契约（Pydantic 模型）。

### 7.2 数据层自身问题

1. **IngestService 是 66KB 的 god class，职责越界**
   同时承担外部抓取编排、DB 读写、运行记录状态流转。`run_daily_ingest`、`refresh_*`、`run_cold_start`、`run_startup_fill` 各自手写一套 `running → success/failed` 状态更新，而 RunService 已有 `mark_running/mark_success/mark_failed`。生命周期逻辑重复且语义不一致（并发跳过被标为 `success` 而非 `skipped`）。

2. **Repository 层未被严格执行**
   一部分查询走 repository，但 `universe_service`、`index_service`、`context_builder`、`backtest_service` 大量直接 `self._db.query(...)`，查询逻辑散落各层，repository 边界形同虚设。

3. **data_quality 模块未进入数据闭环**
   `services/data_quality.py` 的 docstring 声明"在数据摄取后调用"，实际仅挂在 `/system/data-quality` 展示接口，摄取链路未调用，异常检测没有反馈到数据生产流程。

4. **领域模型为引擎接口妥协**
   universe 字典同时包含 `etf_code` 与 `index_code`（值相同）以兼容引擎，本质是把"指数"伪装成"ETF"的兼容层，扭曲了领域语义。

### 7.3 因子层自身问题

1. **FactorService 混了三件事**
   元数据同步（`sync_factor_definitions`）、计算编排、持久化集中在同一服务。元数据治理与因子计算是不同生命周期，耦合后迫使引擎层为补数据反向调用它（见 7.6 C3）。

2. **因子定义存在双重事实来源**
   代码侧（FactorRegistry）与 DB 侧（`factor_definition`）各存一份，靠 `sync_factor_definitions` 手动/隐式对齐。进程启动时注册表先构建，DB 同步状态不受保证，运行时依赖"按需补算"兜底，而兜底本身是写副作用。

3. **同一因子存在三条计算路径**
   DB 预计算值（调度器）、回测预计算值（FactorProvider batch/point）、按需补算值（ContextBuilder 触发）。三者的数据来源与回望窗口可能不同，缺少"同源同算"保证，值可能不一致。

4. **批量协议覆盖不全**
   `BatchFactorComputer` 仅部分因子（momentum 系列）实现，未实现的因子在回测中退化为"日期 × 指数"双重逐点循环，性能分叉明显。

### 7.4 策略层自身问题

1. **引擎硬编码因子语义**
   `_TRANSFORM_REGISTRY`（`engine/score.py`）把 `momentum_score`、`volume_score`、`trend_score`、`sentiment_score` 等因子语义写死在引擎代码中。策略配置只能引用已注册变换名，新增变换必须改代码，与"配置驱动、无需代码"定位部分矛盾。

2. **StrategyService 职责混杂**
   CRUD、star 管理、`run_allocation` 执行、`get_starred_summary` 聚合集中在同一类，同时直接依赖引擎 + ContextBuilder + FactorRegistry，是策略层最重的入口。

3. **配置无 schema 版本**
   `config_json` 以原始 JSON 存库，引擎配置模型演进时靠"前端表单与后端模型手工同步"（AGENTS.md 已承认），没有配置迁移机制。

4. **EngineContext.extra 是无类型逃生舱**
   估值等数据通过 `extra["index_valuation"]` 传递，绕过了结构化契约。

### 7.5 回测层自身问题

1. **BacktestService 是 50KB 的 god class**
   创建、执行、进度、对比、universe 解析、换手率、交易成本、信号准确率、schema 转换全部内聚。metrics/benchmark 已拆出，但成本模型与换手率仍内联在回测循环。

2. **回测执行直接操作 ORM 状态**
   `row.status = "running"; self._db.commit()` 绕过 repository，且与 RunService 的状态流转模式不一致（使用独立 `backtest_run` 表 + 手写状态逻辑）。

3. **执行与绩效计算耦合在每日循环**
   循环内同时算组合收益、基准收益、换手率、信号计数、T+1 执行逻辑，"执行"与"绩效"两个关注点未分离。

### 7.6 层间协作问题（最值得优先修复）

#### C1. 策略执行被三处重复编排

`StrategyEngine()` + `ContextBuilder()` 在三个位置各自实例化、各自构建上下文、各自解释结果：

- `StrategyService.run_allocation`——实时分配，无状态、不持久化；
- `StrategyExecutionService.execute`——持久化信号与因子值；
- `BacktestService._run_backtest_loop`——回测预计算后逐日执行。

缺少统一"策略执行服务"作为唯一入口，导致：

- 实时分配永远重算，已持久化的 `index_signal` 不被复用；
- universe 解析逻辑在 `_build_live` 与 `_resolve_index_universe` 各写一遍；
- 有效日期回退、缺失因子处理逻辑散落多处。

#### C2. 因子层 → 策略层的契约是"值字典"，信息降维

`FactorProvider` 将因子结果压成 `dict[(code, factor_id)] → float | None`，丢失 `FactorValue` 的 text、payload（计算中间数据）与因子元数据。引擎无法区分三种缺失——**因子未计算 / 数据不足 / 因子不存在**，只能靠 `missing_factor_strategy="ignore"` 静默跳过，是校验缺口（P4）的根因之一。

#### C3. 依赖方向倒置：engine 反向依赖 services（形成环）

`engine/context_builder.py` 实时模式在因子缺失时直接导入并调用 `FactorService.compute_and_store()` + `commit()`，调用链变为 `services → engine → services`。该环由"按需补算"跨层 hack 造成，应将补算逻辑提升到 service 层，ContextBuilder 保持只读。

#### C4. 同一张因子值表有两个写入方

`index_factor_value` 同时被因子层（FactorService，`strategy_id=NULL`）与策略层（StrategyExecutionService 回填策略评分值，`strategy_id=策略ID`）写入，语义不同，查询时需显式过滤 `strategy_id IS NULL`。表归属不清，"策略输出"混入"因子结果"。

#### C5. 数据准备逻辑在实时与回测之间重复

回测自行实现 `_load_all_index_bars` / `_load_all_valuation` / `_load_all_macro`，实时模式 `_build_live` 又实现一套（90 天回望、is_active 过滤）。同一批表、同一套过滤条件两处实现，数据模型变更时需同步修改两处，且已出现不一致（`_build_live` 加载估值未按 `index_codes` 过滤）。

#### C6. 领域规则没有真正下沉到 domain

`domain/` 目前仅有枚举、常量与 dataclass；调仓日判定（`DefaultRebalanceScheduler`）、交易成本、换手率、信号等级等真实业务规则散落在 engine 与 backtest_service。domain 层空心化，规则未沉淀为可独立测试的领域对象。

### 7.7 分层问题小结与处理建议

**核心缺陷三点：**

1. 没有统一执行入口——同一引擎被三处各自编排（C1）；
2. 因子契约在传递中降维——rich 的 `FactorValue` 被压成 `float | None`，缺失语义丢失（C2）；
3. 依赖方向有一处倒置——engine 为补数据反向依赖 services，形成环（C3）。

**处理顺序建议：**

1. 统一执行入口：收敛 `run_allocation` / `execute` / 回测执行到同一服务，共享上下文构建与结果持久化；
2. 移除引擎侧按需补算：补算触发上移到 service 层，ContextBuilder 保持只读；
3. 升级因子契约：`FactorValue` 增加缺失原因（missing_reason）与元数据，引擎按三态处理缺失；
4. 收敛 `index_factor_value` 写入方：策略回填数据改独立表或明确语义；
5. 实时/回测共用数据准备逻辑：90 天回望加载下沉到数据访问层；
6. 领域规则下沉 domain：调仓、成本、换手率、universe 解析迁移为纯领域对象；
7. 统一 run 生命周期抽象：状态流转收敛到单一服务。
