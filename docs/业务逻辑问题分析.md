# 业务逻辑问题分析（因子计算 / 策略执行 / 回测正确性）

> 分析日期：2026-08-21
> 范围：因子计算、策略执行（评分/过滤/排名/组合）、回测收益与绩效指标
>
> 总体结论：代码在防未来函数（look-ahead）方面整体合格，但存在若干**确凿的业务逻辑错误**（ERP 取错 LPR、回测未扣交易成本、AI 因子回测不生效、回测回望窗口不足等），**输出结果不能保证正确**，尤其是回测的绝对收益与含 ERP/估值因子的策略信号。

## 二、详细问题说明

### B1. ERP / ERP 百分位因子取错 LPR

**问题现象**

`ERPComputer` 与 `ERPPercentileComputer` 都用以下方式取"最新 LPR"：

```python
latest_lpr = max(lpr_data.values()) if lpr_data else None
```

`lpr_data` 的结构是 `{period: value}`（如 `{"2019-08-20": 4.35, "2024-07-22": 3.45}`），`max(values)` 取的是**数值最大**的一期，也就是历史上最老、最高的一期 LPR，而不是当前生效值。LPR 长期下行，当前实时计算的 ERP 会系统性偏低（股票相对债券看起来更没吸引力）。

此外，回测模式下宏数据没有按 `period <= trade_date` 做时点过滤（`precompute_backtest_factors` 直接透传全量 `all_macro`），即使修好"取最新一期"，历史日期也会用到回测区间内未来才公布的 LPR，属于前视偏差。

**代码定位**

- `apps/api/src/quant_etf_api/factors/builtins/erp.py:71`（ERPComputer）
- `apps/api/src/quant_etf_api/factors/builtins/erp.py:133`（ERPPercentileComputer）
- 回测宏数据透传：`apps/api/src/quant_etf_api/engine/factor_provider.py` `precompute_backtest_factors()` 的 `all_macro` 参数
- 宏数据加载：`apps/api/src/quant_etf_api/factors/service.py` `_load_context()`（实时模式同样未按日期过滤）

**影响**

所有在 timing/score 中引用 `erp` 或 `erp_percentile` 的策略，实时与回测的信号都基于错误的 LPR；`erp_percentile` 的历史分布计算也使用同一个错误 LPR，整个因子不可信。

**解决方式**

1. LPR 取值为"截止 `trade_date` 的最近一期"：`period <= trade_date` 中 period 最大的那条记录，而不是 `max(value)`；
2. 回测预计算时为每个交易日构建时点化宏数据视图（`{code: {period: value for period <= trade_date}}`）；
3. 为 ERP 因子补充单测：构造多期 LPR 数据，断言取的是目标日期前最近一期。

**处理结论（2026-08-26）**

- LPR 取值改为"截止 `trade_date` 的最近一期"：新增 `factors/macro_period.py`（`parse_macro_period` / `latest_value_as_of` / `macro_indicators_as_of`），ERP 因子统一通过 `latest_value_as_of` 取 `period <= trade_date` 中 period 最大的一期，替代 `max(value)`；
- 回测预计算（`precompute_backtest_factors`）按交易日构建时点化宏数据视图，实时模式 `FactorService._load_context` 同样过滤 `period_date > trade_date` 的记录，消除前视偏差；
- 新增 `tests/unit/test_erp.py`：构造多期 LPR，断言取的是目标日期前最近一期。

B1 不再作为待修复问题追踪。

### B2. 回测回望窗口固定 90 天，不满足因子 lookback 要求

**问题现象**

回测加载日线的回望窗口写死为 `_BACKTEST_LOOKBACK_DAYS = 90` 自然日：

```python
lookback_start = trading_dates[0] - timedelta(days=_BACKTEST_LOOKBACK_DAYS)
```

而因子注册表中 `return_120d` 需要约 175 自然日、`ma_60d` 需要约 95 自然日、估值类因子声明 `lookback_days=730`。实时模式 `FactorService._load_context` 按注册表最大 lookback（730 天）加载，回测却没有。

**代码定位**

- `apps/api/src/quant_etf_api/services/backtest_service.py:57`（常量定义）
- `apps/api/src/quant_etf_api/services/backtest_service.py:769-778`（`_load_all_index_bars`）
- `apps/api/src/quant_etf_api/services/backtest_service.py:780`（`_load_all_valuation`，从 `trading_dates[0]` 开始，无回望）

**影响**

回测区间开头的数十到一百多个交易日，长周期因子全部为 `None`：ignore 策略下剩余因子被重新归一化加权，filter 策略下可能整段空仓。回测前段与实盘不可比。

**解决方式**

1. 回望窗口改为 `max(computer.spec.lookback_days for computer in registry.all())` 推导，与实时模式保持一致；
2. 估值数据同样按回望窗口加载（供 `erp_percentile` 等需要历史分布的因子使用）；
3. 回测启动时记录实际回望天数，并在结果元数据中暴露"前 N 个交易日因子数据不足"的提示。

**处理结论（2026-08-26）**

- `factors/registry.py` 新增 `max_lookback_days()`：从注册表推导最大因子 lookback（默认注册表为 730 自然日，空注册表兜底 90 天）；
- `BacktestService._get_lookback_days()` 统一使用该推导值，行情与估值加载共用同一回望窗口（起点 = 回测起点 - 回望自然日），实时与回测口径一致；
- 回测启动时在 `row.params` 中记录 `_lookback_days` 与 `_warmup_trading_days`（各因子首次全指数覆盖日的最大值，暴露前段数据不足提示）；
- 新增 `tests/unit/test_backtest_lookback.py` 覆盖推导、加载窗口与预热期估算。

B2 不再作为待修复问题追踪。

### B3. 交易成本模型未实现（系统暂不考虑实盘交易，仅研究策略理想效果，将交易成本相关的所有内容删除）

**问题现象**

AGENTS.md 与模块 docstring 声称回测集成"交易成本模型（佣金+滑点）"，但全代码库没有佣金/滑点扣减逻辑。回测循环只计算并存储换手率，`portfolio_return` 由 `_compute_allocation_return` 直接计算，从不扣除任何成本。

**代码定位**

- `apps/api/src/quant_etf_api/services/backtest_service.py:611`（`_compute_turnover`，仅计算换手）
- `apps/api/src/quant_etf_api/services/backtest_service.py:591-606`（`_compute_allocation_return`，无成本扣减）
- 主循环写入收益：`apps/api/src/quant_etf_api/services/backtest_service.py:420-430`（`portfolio_return` 直接入库）

**影响**

回测收益是毛收益。高频调仓/高换手策略（尤其 winner_take_all、daily rebalance）收益被系统性高估，回测与实盘差距大。

**解决方式**

1. 实现成本模型：调仓日 `cost = turnover * (commission_rate + slippage_rate)`，从当日 `portfolio_return` 中扣除；
2. 费率参数化（默认如佣金 0.03% + 滑点 0.05%，可配置）；
3. 在 `BacktestMetrics` 中新增 `total_cost_pct` / `avg_turnover` 字段，方便评估成本影响；
4. 补充成本扣减的单元测试（含调仓/非调仓日、双边成本语义）。

**处理结论（2026-08-26）**

系统当前阶段**不考虑实盘交易**，仅研究策略理想效果，因此不再实现交易成本模型，而是**删除交易成本相关的所有代码逻辑与文档声明**：

- `backtest_service.py` 模块 docstring 与 `_run_backtest_loop` 中"交易成本模型 / 扣除交易成本"的表述已移除；
- 未使用的 `_compute_turnover` 包装方法及其"交易成本"分区已删除（换手率仍作为独立研究指标保留，由领域函数 `compute_turnover` 计算并写入每日结果）；
- AGENTS.md 中"交易成本模型（佣金+滑点）"的表述已更新为"回测收益为毛收益"；
- 前端换手率说明中"配合交易成本评估策略的实际可执行性"一句已移除。

回测收益固定为**毛收益**口径（不扣佣金/滑点），B3 不再作为待修复问题追踪。

### B4. AI 情绪因子在回测中不生效（目前没有策略使用AI因子，且AI部分的逻辑并不完善，删除所有AI相关的因子）

**问题现象**

`_run_backtest_loop` 调用因子预计算时未传入情绪数据，`precompute_backtest_factors` 的 `all_sentiment` 参数默认为 `None`，AI 因子（sentiment_1d/5d/divergence、attention_1d/5d、topic_momentum）的上下文为空，全部返回 `None`。

**代码定位**

- `apps/api/src/quant_etf_api/services/backtest_service.py:291`（预计算调用，未传 sentiment）
- `apps/api/src/quant_etf_api/services/backtest_service.py:499`（`_prepare_backtest_data` 返回 6 元组，无 sentiment）
- `apps/api/src/quant_etf_api/engine/factor_provider.py` `precompute_backtest_factors()` 的 `all_sentiment` 参数

**影响**

使用了 AI 因子的策略，回测结果不代表实盘行为（实盘有情绪数据，回测没有），且无任何告警。

**解决方式**

1. 在 `_prepare_backtest_data` 中加载 `DailySentimentAggregateModel`（按区间），传入 `precompute_backtest_factors(all_sentiment=...)`；
2. 预计算时按 `dt <= trade_date` 对情绪数据做时点过滤；
3. 若暂不支持，则在创建回测时显式拒绝包含 AI 因子的策略并给出提示，避免静默失真。

**处理结论（2026-08-26）**

AI 情绪分析功能当前阶段不完善，且没有策略使用 AI 因子，因此**删除所有 AI 因子及其因子系统集成逻辑**：

- 删除 6 个 AI 因子计算器（ai_sentiment_1d/5d/divergence、ai_attention_1d/5d、ai_topic_momentum）及 `ai_factors/registry.py` 注册模块；
- 移除 `FactorContext.ai_sentiment` 字段、`FactorService._load_ai_sentiment` 实时情绪加载、`precompute_backtest_factors` 的 `all_sentiment` 回测参数；
- 移除 AI 因子专用 transform（`sentiment_score` / `attention_score`）与 `FactorCategory.SENTIMENT/ATTENTION` 枚举；
- 策略配置引用 AI 因子将在校验阶段被拒绝（因子不存在），不再存在"回测不生效"的静默失真问题。

AI 舆情分析（新闻采集 / LLM 情绪评分 / 标签分类 / 情绪聚合 / 市场研判）作为独立展示功能保留，前端 AI 舆情页不再提示"策略集成"。

### B5. 实时与回测信号口径不一致

**问题现象**

1. **signal_score 语义不同**：
   - 实时：`signal_score = round(score, 1)`，存的是**综合得分**（`apps/api/src/quant_etf_api/engine/orchestrator.py:268`）；
   - 回测：`signal_score = round(target_weight * 100, 2)`，存的是**仓位权重 × 100**（`apps/api/src/quant_etf_api/services/backtest_service.py:565`）。
2. **信号等级判定输入不同**：
   - 实时传入 `timing_regime`（防守 regime 全部降为 LOW，`orchestrator.py:233`）；
   - 回测 `_write_index_results` 调用 `determine_signal_level` 时未传 `timing_regime`（`backtest_service.py:551`）。

**代码定位**

- `apps/api/src/quant_etf_api/engine/orchestrator.py:233, 268`
- `apps/api/src/quant_etf_api/services/backtest_service.py:551, 565`
- `apps/api/src/quant_etf_api/domain/common/signal_level.py`

**影响**

回测的信号准确率、HIGH/MID/LOW 计数与实盘口径不同，用回测验证信号质量不可靠；`signal_score` 同名字段跨表不同义，前端分析容易误读。

**解决方式**

1. 统一 `signal_score` 语义为综合得分；仓位权重单独存字段（`target_weight`）；
2. `_write_index_results` 传入 `timing_regime`，与实时共用同一 `determine_signal_level` 输入；
3. 增加断言式测试：同一交易日、同一策略配置下，实时与回测的信号等级一致。

**处理结论（2026-08-26）**

已统一实时与回测的信号口径：

- `backtest_index_result.signal_score` 语义从"目标权重 × 100"改为**综合得分**，与实时 `index_signal.signal_score` 完全一致（均 `round(score, 2)`）；
- 新增 `backtest_index_result.target_weight` 列存储信号目标仓位权重，与实时信号 `payload.target_weight` 同义；迁移 0024 回填旧数据（`target_weight = 旧 signal_score / 100`，`signal_score` 由 `original_score` 回填）；
- 冗余列 `original_score` 已删除（其语义与新 `signal_score` 完全重复，前端类型与说明同步移除）；
- `_write_index_results` 与实时 `_build_strategy_results` 共用同一 `determine_signal_level` 输入：score / target_weight（当日目标仓位，即 `result.positions`）/ has_positions / timing_regime / scoring_mode；防守 regime 下回测同样全部降为 LOW；
- 回测 `in_portfolio` 语义调整为"信号是否纳入当日目标组合（目标权重 > 0）"，信号准确率统计与实时信号口径一致（执行层面实际持仓仍由 `backtest_daily_result.positions` 记录）；
- 新增 `tests/unit/test_signal_consistency.py`：同一交易日、同一策略配置下，断言实时与回测的 signal_score / signal_level / target_weight 完全一致，并覆盖防守 regime 全 LOW 场景。

B5 不再作为待修复问题追踪。

### B6. 缺失因子三态不可分，filter 遇 None 即失败

**问题现象**

1. 因子值跨层传递为 `dict[(code, factor_id)] → float | None`，引擎无法区分"因子未计算 / 数据不足 / 因子不存在"三种缺失；
2. filter 规则中因子值为 `None` 时 `_check_rule` 直接返回 `False`（AND 下资产被排除、OR 下该规则失败）；
3. score 的 `ignore` 策略把缺失因子从分母剔除，剩余因子权重被重新归一化，同一策略在不同数据覆盖下评分含义漂移。

**代码定位**

- `apps/api/src/quant_etf_api/engine/filter.py:57-76`（`_check_rule`，None 返回 False）
- `apps/api/src/quant_etf_api/engine/filter.py:188`（AND 短路返回 False）
- `apps/api/src/quant_etf_api/engine/score.py:341-380`（missing_factor_strategy 三种分支）
- `apps/api/src/quant_etf_api/engine/factor_provider.py` `load_asset_factors()`（值字典契约）

**影响**

数据缺口（如 399006/399001 无估值）在 filter 用了估值因子时一票否决整只指数，组合可能悄悄变空；缺失原因不可排查，策略"看起来正常但结果为空"。

**解决方式**

1. `FactorValue` 增加 `missing_reason`（missing / insufficient_data / unknown_factor），跨层传递保留该字段；
2. filter 支持显式 missing 策略（pass / fail / exclude），而不是无条件 False；
3. 配置校验时用注册表兜底因子存在性（快速失败），避免"因子不存在"进入运行期静默路径。

**处理结论（2026-08-26）**

三态缺失基础能力此前已落地（`FactorValue.missing_reason` / `MissingReason` 枚举 /
`ContextBuilder.detect_missing_factors` 只读检测 / P4 校验拦截未知因子），本次补齐剩余部分：

- `FilterRule` 新增 `missing_strategy`（`pass` / `fail` / `exclude`，默认 `fail`，存量策略行为不变）；`StrategyConfigService` 结构校验对非法值报 422；
- `DefaultFilterEngine` 对因子值或 `compare_to` 参照值为 `None` 的规则按 `missing_strategy` 判定，`FilterRuleResult` 增加 `missing` / `missing_strategy` 字段，`fail_reason` 输出"因子缺失(missing_strategy)"文案，前端调试面板可直接看到被过滤原因；
- 实时策略 `AllocationResponse` 新增 `warnings`：`detect_missing_factors` 检出 NOT_COMPUTED / INSUFFICIENT_DATA 时随响应返回结构化警告；
- 回测执行期收集结构化警告（`WARMUP` / `MISSING_FACTOR` / `DATA_GAP` / `BENCHMARK_MISSING`，失败时 `PARTIAL_RESULT`），写入 `backtest_run.warnings` 列（迁移 0025），`BacktestDetail` 返回给前端；
- 前端同步：`StrategyConfigForm` 过滤规则增加"缺失时"下拉（不满足/通过/排除），`StrategyDetailPage` 只读展示；
- 新增测试：`test_engine_filter.py` 覆盖 missing_strategy 三值 × AND/OR × 固定阈值/跨因子比较与调试标记，`test_p4_factor_validation.py` 覆盖非法值校验，`test_backtest_warnings.py` 覆盖警告聚合与持久化。

B6 不再作为待修复问题追踪。

### B7. 横截面模式对全缺失资产的处理与 absolute 不一致

**问题现象**

- absolute 模式（`DefaultScoreCalculator`）：所有因子缺失 → 返回 `None` → 资产被排除；
- rank/zscore 模式（`CrossSectionScorer`）：所有因子缺失时 `total_weight == 0` → `raw_score = 0.0` 并进入横截面（`engine/score.py:539-543`），得到最低分但**不会被排除**，top_n 恰当时可能进入组合。

**代码定位**

- `apps/api/src/quant_etf_api/engine/score.py:539-543`（raw_score 置 0）
- `apps/api/src/quant_etf_api/engine/score.py:460-480`（exclude 分支仅作用于"任一因子缺失"）

**影响**

同一数据缺口下，absolute 与 rank/zscore 策略的资产池行为不同，轮动类策略可能把数据缺失的指数纳入组合。

**解决方式**

1. 横截面评分器对全缺失资产同样返回排除语义（不写入 `raw_scores`），与 absolute 一致；
2. 补充测试：全缺失资产在三种 scoring_mode 下均不进入排名与组合。

**处理结论（2026-08-26）**

- `CrossSectionScorer.calculate()` 在 `total_weight == 0`（默认 ignore 策略下全部因子缺失）时不再写入假 0 分，改为排除该资产并输出 `excluded=True`、`exclude_reason="因子数据全部缺失"` 的调试明细，与 `DefaultScoreCalculator`（absolute）行为一致；`zero`/`exclude` 策略语义保持不变；
- 新增 `tests/unit/test_engine_score.py::TestCrossSectionScorer`（rank/zscore 全缺失排除、zero 策略保留、部分缺失保留、调试标记）与 `tests/unit/test_engine_orchestrator.py::test_all_missing_asset_not_selected`（三种 scoring_mode 下全缺失资产均不进入排名与组合，`bottom_n` 不再误选缺失资产）。

B7 不再作为待修复问题追踪。

### B8. 估值百分位双源口径不一致

**问题现象**

1. legulegu 覆盖的 12 个指数与中证官网覆盖的其余指数，百分位口径不统一：
   - 中证官网自算百分位使用 `percentile = count_less / i * 100`（分母不含当日、并列值不计入），最高值只有在严格单调上升时才等于 100，首日强制 50；
   - legulegu 源历史上曾透传上游百分位，与自算口径不可比。
2. 两条源路线的原始 PE 口径不同：legulegu 取上游返回的"静态市盈率"，中证官网取"滚动市盈率（TTM）"；且 `index_valuation.source` 一直写死为 `akshare`，无法按来源区分。

两套来源的百分位定义不同，直接跨指数比较（如 rank 模式、估值吸引力排序）会失真。

**代码定位**

- `apps/api/src/quant_etf_api/infra/clients/akshare_index.py`（`_calc_percentile` 统一百分位函数）
- `apps/api/src/quant_etf_api/infra/clients/akshare_index.py:571`（`fetch_index_valuation` 双源降级入口）
- `apps/api/src/quant_etf_api/services/ingest_service.py`（`_fetch_and_upsert_index_valuation` 写入 source）

**影响**

混合使用两套口径的 `pe_percentile` 做横截面比较时，数值不具备可比性。

**解决方式**

1. 统一百分位定义：`rank / (n - 1) * 100`（含当日、可达 100），legulegu 数据也按统一算法重算；
2. `index_valuation` 记录 `source` 字段，策略/前端按来源区分或过滤；
3. 评估影响后决定是否在横截面评分前对百分位做来源归一化。

**处理结论（2026-08-26）**

- 百分位统一：新增模块级 `_calc_percentile()`（`infra/clients/akshare_index.py`），两条源共用同一算法 `rank / (n - 1) * 100`——样本为截至当日（含当日）的有效值（无前视偏差）、rank 为 0-based（并列值计入自身，最高值可达 100、最低值为 0）、首日无历史可比返回 50.0；实现改为有序插入 O(n log n)，替代原 O(n²) 逐日重扫；
- source 真实化：`IndexValuation` 增加 `source` 字段，legulegu 路径写 `legulegu`、中证官网路径写 `csindex`，摄取写入改用 `v.source` 落库（不再写死 `akshare`）；
- 存量数据修复：新增 CLI 命令 `python -m quant_etf_api.cli recompute-valuation-percentiles`，基于已入库的 pe/pb 原始值按统一算法重算全部历史百分位并回填 source（幂等，可重复执行）；
- 已知遗留：legulegu 原始 PE 仍为"静态市盈率"、中证官网为"滚动市盈率（TTM）"，两者绝对值口径不同；"来源归一化/按源过滤"（解决方式第 3 点）暂不实施，现依赖 `source` 字段由策略/前端自行区分；
- 注意：已保存的回测结果（`backtest_daily_result` / `backtest_index_result` 的信号与得分）基于旧口径百分位，不会追溯重算，需重跑回测才反映新口径。

B8 不再作为待修复问题追踪。

### B9. next_day 执行语义与文档不符

**问题现象**

Schema 注释宣称"T 日信号 T+1 日**开盘**执行"，但收益计算全部基于收盘价：调仓日 T 用旧仓位吃 T→T+1 收益，新仓位到 T+1 才开始吃 T+1→T+2 收益，**实际是 T+1 收盘执行**。

**代码定位**

- `apps/api/src/quant_etf_api/services/backtest_service.py:363-392`（next_day 分支的 pending 逻辑）
- `apps/api/src/quant_etf_api/schemas/backtest.py`（`execution_model` 注释）

**影响**

回测执行时点比宣称晚一个交易日，信号衰减/隔夜跳空没有被正确模拟，结果与"贴近实盘"的预期有系统性偏差（保守方向）。

**解决方式**

1. 修正文档/注释，明确当前为"T+1 收盘执行"；
2. 若要实现真正的 T+1 开盘执行，需引入 `open_price` 作为成交价并调整收益计算；
3. 在回测详情中展示实际执行模型，避免用户误读。

### B10. 数据缺口静默按 0% 收益

**问题现象**

`_compute_allocation_return` 中指数当日 bar 缺失时 `ret is None`，该权重的收益被**跳过**（等价于按 0% 处理），但仓位仍显示为持有；基准 `compute_buy_hold_benchmark` 对缺失 bar 补 0%。两者口径一致但都不提示数据缺口。

**代码定位**

- `apps/api/src/quant_etf_api/services/backtest_service.py:591-606`（`_compute_allocation_return`）
- `apps/api/src/quant_etf_api/services/benchmark.py` `compute_buy_hold_benchmark()`（缺失补 0）

**影响**

指数上市晚或数据断档期间，组合曲线与基准曲线失真且无告警，用户可能把数据问题当成策略表现。

**解决方式**

1. 回测启动时检查区间内数据覆盖率，缺失超过阈值直接拒绝或警告；
2. 每日结果中记录 `missing_bar_count`，在指标中暴露"数据缺口天数"；
3. 明确缺失收益的语义（0% 或按持有处理），并在文档中说明。

### B11. 胜率/夏普包含空仓日

**问题现象**

`_calc_win_rate` 对全部交易日统计正收益占比，空仓日收益 0 不算正收益，被当作"失败日"稀释胜率；Sharpe 同样包含空仓零收益日，压低波动、抬高夏普。代码已计算 `active_rets` 却只用于 `active_days`。

**代码定位**

- `apps/api/src/quant_etf_api/services/metrics.py:199`（`_calc_win_rate`）
- `apps/api/src/quant_etf_api/services/backtest_service.py:700-715`（`_compute_summary_metrics` 传入全量 `daily_rets`）

**影响**

胜率被低估、夏普被高估，指标间口径不一致。

**解决方式**

1. 胜率改为基于 `active_rets`（仅持仓日）计算；
2. Sharpe 明确选择口径（全期 vs 持仓期），并补充说明；推荐同时暴露两个口径或统一为持仓期；
3. 补充指标口径的单元测试。

**问题现象**

**影响**

**解决方式**

2. 前端展示"数据日期"徽标，回退时提示"最新数据截至 X 日"。

### B13. same_day 模式带未来函数

**问题现象**

same_day 模式：T 日收盘信号当天生效并吃 T→T+1 收益，属于经典前视偏差。代码已在注释中标明"学术简化"，默认执行模型为 next_day。

**解决方式**

### B14. 月线聚合将空 OHLC 记为 0

**问题现象**

月线聚合 `_aggregate_monthly_bars` 使用 `bar.high_price or 0.0` / `bar.low_price or 0.0`，某日 high/low 为空时 0 会进入月线极值计算，扭曲月线 OHLC。

**代码定位**

- `apps/api/src/quant_etf_api/factors/builtins/monthly.py:62`

**影响**

**解决方式**

2. 为 `_aggregate_monthly_bars` 补充缺数据场景测试。

## 三、输出可信度评估

### 相对可信

- 技术类/动量类因子数值（无未来泄漏，回望窗口充足时）；
- absolute 评分模式下、数据完整时的单日分配结果；
- 回测结果的**相对排序**（同一策略不同参数横向比较，数据覆盖一致时）。

### 不可信 / 需打折扣

- 任何使用 `erp` / `erp_percentile` 因子的策略（B1 已修复：LPR 改为截止交易日的最近一期，实时+回测一致）；
- 任何回测的**绝对收益与夏普**均为毛收益口径（B3 已决策不扣交易成本，仅研究理想效果）；
- 使用 AI 因子的策略回测（B4 已删除所有 AI 因子，策略配置引用会被校验拒绝，不再存在此问题）；
- 回测区间前段的信号与绩效（B2 已修复：回望窗口按因子 lookback 推导；历史数据本身不足时，结果中会暴露预热期提示）；
- 回测信号准确率（B5 已修复：signal_score 与信号等级口径和实时一致）；
- 数据断档期的组合收益与基准对比（B10，静默补 0）。
