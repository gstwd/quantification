# 数据管理与外部数据接入规范

## 目标与边界

数据管理体系负责**非新闻外部数据**从入库、质量检查到人工维护的闭环。新闻、AI
分析结果、因子、策略、回测等派生数据不属于本体系。当前受管数据集由
`DataManagementService.DATASETS` 静态清单定义：交易日历、指数日线/估值/成分、
宏观指标、申万行业基础信息/日线/成分、证券基础信息和个股日线收盘。

“上游来源”与“逻辑数据集”必须分开：同一个逻辑数据集可有多个上游回退来源，
状态展示以最近一次真实抓取使用的来源为准，不对外部接口做额外定时探测。

## Tushare 优先接入约定

已配置 `QUANT_ETF_TUSHARE_TOKEN` 时，除申万行业日线（`sw_daily` 在 2000 积分
档位无权限）外的受管数据集统一按“Tushare 优先、既有来源兜底”编排，客户端只做
拉取与字段归一化，优先级判断放在服务层：

| 数据集 | Tushare 接口 | 兜底来源 |
| --- | --- | --- |
| A 股交易日历 | `trade_cal` | AkShare 新浪 |
| 指数日线行情 | `index_daily` | AkShare / TickFlow / Baostock |
| 指数估值 | `index_dailybasic`（仅 000300/000016/000905） | 乐咕乐股 / 中证官网 |
| 宏观指标 | `cn_cpi` / `cn_pmi` / `shibor_lpr` | AkShare |
| 指数成分 | `index_weight` | AkShare csindex / Baostock |
| 证券基础信息 | `stock_basic` | 交易所 / AkShare |
| 个股日线收盘 | `daily` | Baostock / AkShare |
| 申万行业日线 | 不可用（sw_daily 无权限） | 申万官网 / AkShare |

兼容性要求：Tushare 的成交额（千元）与成交量（手）必须换算到
`index_daily_bar` 的统一口径（元/手）；估值 `pe` 映射 Tushare `pe_ttm` 列（与
既有 legulegu 序列平均差异最小），百分位仍按历史滚动口径计算；成分权重由百分比
转为 0-1；交易日历以 SSE 口径与 AkShare 对齐。

## 健康快照与操作

`data_health_snapshot` 仅保存当前状态；任务历史由 `research_run` 与
`research_run_item` 保存。每个数据集有一个汇总行，具备可维护对象的数据集还会有
分区行。快照包含实际/目标日期、记录数、缺口/异常数、最近检查和最近运行结果。

**质量口径唯一性**：`data_health_snapshot` 是全系统**唯一**的数据质量口径。
各页面（数据管理页、指数详情页、行业详情页等）只读取该快照，不得自行重算质量；
历史上并行的独立口径已全部退场：

1. `GET /system/data-quality`（`DataFreshnessService` 重算新鲜度与字段空值率）——已删除；
2. `GET /market-data/indexes/{code}/data-quality`（重算 OHLC 缺失）——已删除；
3. `GET /industry/indexes/{code}/quality`（`IndustryDataService.industry_quality_detail`
   读 `industry_universe` 快照列并每请求重算 OHLC/change_pct 缺失）——已删除；
4. `industry_universe` 的 5 个质量列（`data_start_date` / `data_end_date` / `bar_count` /
   `missing_day_count` / `quality_checked_at`，由 `IndustryDataService._persist_quality_snapshots`
   写入）——迁移 0052 迁入统一表后删列（个股侧同性质列已由迁移 0042 删除）；
5. `StockDataService._persist_quality_snapshots` 作为 `data_health_snapshot` 的
   **第二个写入者**（规则更弱：`invalid_count` 恒置 0、不更新汇总行）——已删除，
   个股质量只由 `DataManagementService` 的 `check` 操作写入。

字段级合法性规则统一实现在 `DataManagementService._quality_conditions`（按数据集给出
硬错误与告警条件，由数据库执行），缺口统计统一走 `_missing_count_from_bounds` /
`_exact_missing_date_values`（按交易日历反连接）；`domain/market_data/quality.py`、
`domain/industry/quality.py`、`domain/stocks/quality.py` 三份平行 Python 规则实现均已删除。

健康状态含义：

| 状态 | 含义 |
| --- | --- |
| healthy | 已满足该数据集的时效与字段质量规则 |
| warning | 存在日期落后或连续性缺口，需人工确认 |
| error | 无数据、字段非法或最近维护失败 |
| unknown | 尚未执行统一质量检查 |
| unsupported | 上游明确不支持该对象，例如没有估值覆盖的指数 |

**快照生成时机**：快照**不会**在后端启动时自动生成（lifespan 只入队
`warm_calendar`，不执行数据维护任务），只在两种情况下更新：

1. 人工通过 `POST /api/data-management/operations` 提交维护操作（check /
   sync_latest / repair_gaps / rebuild）；
2. 数据摄取任务执行完成，即调度器每日 17:30 入队的全局同步（`data_sync_all`，
   内部以 `sync_latest` 逐数据集执行并刷新快照）。

因此首次部署完成后 `data_health_snapshot` 可能为空：`GET /api/data-management`
通过 `snapshot_count`（0 表示从未生成快照）显式暴露该状态，前端据此给出
"尚未生成健康快照，请手动检查或等待数据同步"的友好提示，而不是把 `unknown`
渲染成异常。

维护操作统一通过 `POST /api/data-management/operations` 提交：

- `sync_latest`：补到数据集的目标日期；全局范围允许。定时任务每日北京时间 17:30 触发
  全局同步，同步完成后自动重算健康快照。低频数据集（成分/目录）在 7 天刷新周期内
  自动跳过上游拉取，只有人工“补最新”才会强制。
- `check`：只扫描并刷新快照；全局范围允许。
- `repair_gaps`：重新扫描完整缺口后进行定向补数；不会由定时任务自动执行。
- `rebuild`：先抓取并校验，再事务内替换旧数据；只允许数据集或单分区范围，确认令牌为 `REBUILD:<dataset_key>:<partition_key 或 ALL>`。

**单一入口原则**：上述四类操作是外部数据同步与维护的唯一入口。原按类型拆分的旧入口
（`POST /api/runs/daily-ingest`、`/runs/index-refresh`、`/runs/macro-refresh`、
`/runs/cold-start`、`/runs/indexes/{code}/rebuild`、`/runs/indexes/{code}/incremental-fill`
及其后台任务处理器）已全部删除，避免两套入口各自持锁并发写同一批表。
`IngestService` 相应收敛为纯抓取后端：只负责多源拉取、字段归一化、幂等写入与
GET 读穿透补数（`data_fill`），不再承担运行状态流转、缺口判断与批量编排。
历史 `research_run` 中的旧 `run_type` 仅用于展示，不再支持重试。

全局同步逐数据集写入运行子项：全部成功为 `success`，部分失败为
`partial_success`，全部失败为 `failed`。任何子项失败都会写入对应健康快照。
行业日线、行业成分和个股收盘这三项关键输入全部成功后，系统才会入队行业面板因子
计算；其中任一项失败则跳过，避免把不完整输入传入因子链路。
指数日线或估值有新增记录时，全局同步按库内实际最新指数交易日入队通用因子计算，
避免在数据源尚未补齐当日行情时按“今天”空跑。

## 新外部数据集接入清单

新增数据集必须同时完成以下项目，不能只添加抓取客户端：

1. 明确逻辑数据集、数据表、分区键、业务频率、目标日期/版本规则和上游回退来源。
2. 在 `DATASETS` 增加静态定义，并在 `DataManagementService` 实现同步、检查、分区枚举、字段异常与安全重拉逻辑。
3. 确保所有外部写入经过 repository/service，记录真实来源和入库时间。
4. 接入统一后台操作；全局同步须能写入 `research_run_item`，失败须刷新健康快照。
5. 为数据集和分区补充 API 可见性，前端数据管理页必须自动展示其摘要、可用操作和问题数。
6. 添加目标日期、缺口、异常、失败保留旧数据、全局部分成功的测试；更新本规范与用户手册。

若数据无固定发布周期（例如 LPR 事件），不得使用交易日新鲜度误报，应以最近成功抓取与字段合法性为主要规则。
