# 决策记录

本文件记录平台层面已经定下的决策，供人和 AI 在提出改动前查阅。分级与准入门槛见 [AGENTS.md「冻结与变更准入」](../../AGENTS.md)。

使用规则：

- 每条只写结论、理由和重新评估条件，不写排障过程。
- 冻结项的任何变更都登记在「冻结项变更」。
- 被否决的提议登记在「已否决提议」。除非条目写明的重新评估条件已经出现，AI 不得再次提出同一提议。
- 「待确认」里是 AI 起草的候选，**还没有约束力**。用户逐条确认后移到对应小节，或直接删除。

## 冻结项变更

### 2026-11-28 永久下线 AI 舆情分析层

- 变更：删除 AI 舆情的前后端页面、API、新闻采集、LLM 分析、标签映射、独立调度器、后台任务处理器、配置与运行依赖；迁移 `0067_remove_ai_sentiment` 删除 `news_item`、`ai_sentiment_result`、`daily_sentiment_aggregate`、`market_synthesis`、`keyword_tag_config`，并清理共享运行表中的 `ai_analysis` 记录。指数详情页使用的“前一交易日”查询迁至 `GET /api/market-data/previous-trading-day`。
- 具体阻塞：用户明确要求系统中不再保留 AI 舆情功能；继续保留会维持外部新闻/LLM 调用、独立调度任务和约 2.1 万条不再使用的历史数据。
- 口径影响：不涉及策略、因子或回测口径，不升口径版本号，金样本不重写。已删除的新闻与舆情历史数据不可恢复；历史迁移和本决策记录仅用于审计与全新数据库迁移链。
- 决定：用户于 2026-11-28 在对话中确认完整删除。

### 2026-11-05 持仓日判定排除零权重持仓

- 变更：判断"当日是否持仓"改为"执行后持仓里至少有一个正权重"，统一使用 `domain/portfolio/accounting.has_positive_weight`。涉及回测主循环、组合策略回测和研究批量重建累积器三处。数据缺口资产计数（`count_missing_allocation_assets` / `count_missing_rebalance_assets`）同样跳过零权重资产。
- 具体阻塞：在库内 493 个 drift_v1 回测上跑独立对账（`backtest verify`），有 234 个的 `active_days` 和 `win_rate_pct` 与逐日结果不符。原因是择时降到零仓位时，执行器的持仓是 `{'000852': 0.0}` 这样的零权重字典，主循环用 `bool(持仓)` 判断，把空仓日算成了持仓日，胜率分母因此混入空仓日。例如 `csi1000_pure_timing_weighted__opt_b15abd84__opt_3fd58b95` 报告的胜率是 14.01%，持仓日胜率实际是 60.93%；报告的持仓天数是 1213，实际是 279。研究批量从取整后的逐日行重建累积器，那条路径原本就是对的，所以落库回测和研究批量的胜率并不一致。胜率只统计持仓日是既定规格（见[策略架构](指数量化系统策略层架构设计.md)「回测与可比性」），规格本身没变，这是实现缺陷。
- 口径影响：只影响 `active_days`、`win_rate_pct`，以及零权重资产恰好碰上行情缺口时的 `data_gap_days` 和逐日 `missing_bar_count`。收益、回撤、夏普、换手和 10 项验收清单都不受影响。不升口径版本号，因为规格没变，旧值是错误值，不是另一种口径；受影响的旧回测可以用 `backtest verify` 逐个识别，重跑即可修正。金样本基准重写，差异只出现在 `timing_weighted_open` 的 `active_days`（119 → 93）和 `win_rate_pct`（47.06 → 59.14）。
- 决定：用户于 2026-11-05 在对话中确认"修复并登记"。

### 2026-11-06 研究数据清理改为只瘦身逐指数明细

- 变更：
  - 策略详情页「清理研究数据」（`DELETE /api/strategies/{id}/research-data`、`StrategyConfigService.clear_research_data`）移除，改为「研究数据瘦身」（`GET|POST /api/strategies/{id}/research-slim`、`backtest slim`）：只删除研究线回测的 `backtest_index_result` 逐指数明细并记 `backtest_run.index_detail_pruned_at`（迁移 0066）。稳健性批次、优化会话、研究台账、战役记录、草稿策略、回测汇总与逐日结果全部保留。被瘦身回测的归因与逐指数结果返回 410。
  - 研究战役结束时自动清理（`campaign_auto_cleanup_enabled`）：本战役回测对应的已结束任务记录、`candidates/<战役>/steps/` 会话日志、战役期间回测的逐指数明细。每日同步后删除超过 `job_history_retention_days` 的已结束任务与超过 `alert_retention_days` 的已读告警。
  - 删除策略增加保护：LIVE / SUSPENDED、仍有成员的研究线根、自身已有试验的策略拒绝删除（409）。
  - 战役模式白名单移除 `strategy prune-variants`；`backtest slim` 不在白名单内。
- 具体阻塞：
  - 旧清理会删除 `robustness_run` 与 `strategy_optimization`，直接降低研究线 N；删除策略同样会把其试验移出 N。两者都违反「研究台账与 N 统计」冻结项。
  - `prune-variants` 在战役模式下不按研究线校验批次，`--force` 时 agent 可删除其他研究线的回测（DSR 校准输入）。
  - 728 条回测的逐指数明细占 3.7 GB，而 N、验收清单、DSR 校准与 `backtest verify` 都不读它，需要一个不伤证据的清理入口。
- 口径影响：不涉及回测计算口径，不升口径版本号，金样本不重写。N 的统计规则不变，只是不再有入口能删除其证据。
- 决定：用户于 2026-11-06 在对话中确认（只做日常瘦身、不做一键重置；旧按钮改为瘦身；战役结束自动清理三项；每日留存任务历史与已读告警）。

### 2026-11-08 指数估值主来源改为中证官网

- 变更：`AkShareIndexClient.fetch_index_valuation` 不再调用乐咕乐股（`stock_index_pe_lg` / `stock_index_pb_lg`），全部指数只取中证官网日线附带的滚动市盈率；Tushare `index_dailybasic` 仍只为 000300/000016/000905 兜底。原乐咕乐股覆盖的 000300、000016、000905、000852、000903、000015 删除存量乐咕行后经 `operations` 全量重拉为中证官网序列；399673（创业板50）中证官网与 Tushare 都不覆盖，删除存量乐咕行，快照为"上游不支持"。中证官网估值请求失败改为抛出异常（官网返回空数据仍视为无数据），避免 `repair_gaps` 把请求失败的日期登记为上游缺失；估值 `repair_gaps` 只在中证官网抛错或整体返回空时才用 Tushare 兜底，不再逐日补官网没有的日期（逐日补会把两种 PE/百分位口径按天混用）；已确认的上游缺失在数据管理页显示为"上游缺失 N 天（仅提示）"，不计入缺口。
- 具体阻塞：数据同步中 000015、000852、000903、399673 的估值持续失败（`AttributeError: 'NoneType' object has no attribute 'attrs'`，乐咕网页返回 504，AkShare 取不到 CSRF 令牌），停在 2026-10-09；接口可用时也只返回月度样本，000016、000300、000905 十月只入库 7 条，估值序列无法按日更新。
- 口径影响：这 6 个指数的 PE 由乐咕静态市盈率改为中证官网滚动市盈率，PE 百分位按新序列重算；PB 与 PB 百分位为空；历史起点从 2005 年前后缩短到 2011–2012 年。`pe_percentile`、`pb_percentile`、`valuation_percentile` 因子取值随之改变。回测计算口径不变，金样本不重写；4 个活跃策略都不引用估值因子。
- 决定：用户于 2026-11-08 在对话中确认（6 个指数改用中证官网；399673 中证官网没有数据就清空；上游缺口只提示、不显示为需关注）。

### 2026-11-08 已确认的上游问题只提示

- 变更：`repair_gaps` 在全部来源请求成功后确认的上游问题不再计入健康状态。"上游缺失"日期本就不计入缺口，现以 `issue_summary.upstream_missing_count` 在数据管理页显示"上游缺失 N 天（仅提示）"；指数 / 行业日线"上游仅收盘价"的行从告警改为只提示（`close_only_count`，"上游仅收盘价 N（仅提示）"）。数据集汇总行累加这两项计数。15%~30% 涨跌幅告警未经确认，保持告警；同步请求失败不视为已确认的上游问题，仍按维护失败展示。
- 具体阻塞：13 个指数日线分区（930601、931151 等）的开高低已逐源确认上游不提供，`repair_gaps` 无法再修复，却持续显示"需关注"，掩盖了真正需要处理的问题；指数估值 2011–2012 年中证官网缺失的日期确认后在页面上完全不可见。
- 口径影响：只改健康快照的状态判定与展示，不涉及回测口径与因子取值，不升口径版本号，金样本不重写。回测仍按原规则剔除缺开盘价或缺最高 / 最低价的日期并给出警告。
- 决定：用户于 2026-11-08 在对话中确认（"数据有问题但确认是数据源问题就只提示，不作为异常或关注"）。
- 补充（同日，用户确认"Repair + suspension fix"）：个股三张日频表的 `repair_gaps` 复验到最近交易日，最新日期之后（停牌等）经全市场响应确认没有该证券的日期记为上游缺失；某交易日全市场为空时视为上游尚未发布、不确认。尾部全部确认时不判"数据已过期"，提示"最新日期后停牌或上游无数据 N 天"。只用于个股，因为指数 / 行业修复按单个分区请求，无法区分"停更"与"上游尚未发布"。阻塞：*ST岭南、*ST清越、TCL中环等 7 只停牌股长期显示需关注。

## 已否决提议

- **调整第 8 项 Deflated Sharpe 门槛**（`acceptance_min_deflated_sharpe`）：不做，保持 0.95。2026-10-24 用 `research dsr-calibrate` 校准（7 个优化会话、11 个稳健性批次，成本 0.5bp）：
  - 假阳性率：N=1 时 0.95 门槛中位数 4.7%（最大 10.5%，厚尾成簇序列偏松）；按研究线 N（47–68）时约为 0；稳健性批次"挑最优 + N=批次变体数"时 0.95 门槛约 1%、0.90 门槛约 3%（最大 3.9%）。
  - 功效（研究线 N）：注入年化超额夏普 1.0 / 1.5 / 2.0 时，0.95 门槛通过率中位数 21% / 75% / 98%，0.90 门槛 33% / 84% / 99%。相关变体按独立试验计入 N，使第 8 项偏保守。
  - 2026-10-25 用户决定维持 0.95。重新评估条件：用户主动提出。
- **因子值落库或缓存**（因子值表 `index_factor_value`、因子值补算队列、缓存失效链路）：不做。因子值一律由原始数据现算，见 AGENTS.md「策略、因子与回测」。重新评估条件：某项具体研究因现算耗时无法完成，且已经排除计算实例复用不足这个原因。

- **重新接入乐咕乐股作为指数估值来源**：不做。其接口只提供月度样本、网页经常 504，接入后序列无法按日更新，且与中证官网滚动市盈率口径不同、不能混用。重新评估条件：乐咕乐股恢复稳定的日频接口，且有研究明确需要 PB。

- **按行数拆分大文件**（`services/backtest_service.py` 约 3200 行、`services/data_management_service.py` 约 3200 行、`cli.py` 约 2750 行、`services/strategy_config_service.py` 约 1500 行）：不做。行数本身不构成阻塞；拆分要改大量调用点和测试里对私有方法的打桩，回归风险高，又没有研究收益。重新评估条件：某个具体需求因文件结构无法安全完成。
- **合并或重命名按审查轮次命名的测试文件**（`test_f_*_fixes.py`、`test_*_review_fixes.py` 等）：不做。只是整理，没有行为收益，还会打断 git blame / log 追溯。新测试仍按被测模块命名（见编码规范「测试规范」）。重新评估条件：无。
- **把路由层直连 repository 的写法收敛进服务层**（`api/routers/` 下仍存在的 `factors`、`indexes`、`industry`、`market_data` 文件）：存量保持原样，新增路由不得再直连。这条只靠文字约束，不进分层守卫。重新评估条件：出现事务或口径不一致的缺陷。
- **单独立项消除分层守卫的两条历史例外**（`factors/compute.py` → 面板服务、`services/robustness_service.py` → `cli_pool`）：不做。只有相关模块因具体需求必须修改时才一并处理，处理后从 `_KNOWN_EXCEPTIONS` 删除。

- **引入新的通用基础设施**（插件框架、统一配置中心、事件总线、依赖注入容器、import-linter、收紧现有 `[tool.mypy]` 配置）：不做。现有扩展点和测试守卫已经够用；现有 mypy 配置保持不变。重新评估条件：出现现有扩展点表达不了的具体需求。
