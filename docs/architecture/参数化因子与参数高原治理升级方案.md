# 参数化因子与参数高原治理升级方案

## 1. 背景、目标与边界

当前策略优化主要通过调整评分权重、增删因子、调整阈值等方式完成。均线等窗口型因子仍以
`ma_5d`、`ma_10d`、`ma_20d` 等独立因子注册。这样的方式使 MA(37)、RSI(11) 等研究需要
新增固定因子，且难以把“因子定义本身”纳入受控的优化流程。

本方案将策略优化升级为：在明确参数空间和审计约束下，调整因子参数；以连续、跨窗口稳定的
**参数高原**替代单点最优；上线后只监测与预警高原漂移，绝不自动改写策略参数。

系统范围不变：只研究具有实际 ETF 对应物的 A 股指数，日频，不含个股、ETF 或交易执行。

### 1.1 硬约束

- 研究期固定为 2016-01-01 至 2025-12-31；2026-01-01 起的数据为验证/监控数据。
- 验证数据可否决策略或触发复核，不能用于自动确认新的最优参数。
- LIVE 策略不得直接修改 `config_json`；参数更新必须产生新的不可变策略修订，保留完整证据和审计轨迹。
- 系统只自动计算、提示和创建候选研究任务；是否调整参数由人工审批。
- 策略“版本”必须是不可变修订实体，而不是覆盖 `strategy_config.version` 字符串；每个修订均可
  独立引用配置快照、因子定义和回测证据。
- **本次升级的迁移范围只含一条策略**：仅把 `mainline_rs_rotation_v12` 迁移到新架构，
  并以它做迁移前后的一致性回测验证；其余策略、草稿变体与历史回测数据一律**不复用、不迁移**。
- **因子中心采用世代隔离重建**：不复用历史 `factor_definition` 行；按新模板/实例身份建立新的
  因子世代，迁移策略切换到新世代，旧世代只读保留至完成退役与归档，并同步适配前端页面。
- 同一经济假设下的所有策略修订、草稿、扫描与重跑共享不可变的 `hypothesis_family_id`；
  **台账归属不得通过新建策略修订、复制策略或更改策略 ID 而改变**。
- 参数空间必须预先声明并受约束，不提供无限制的任意参数穷举。
- **高原判据必须先冻结、后扫描**：容差、最小宽度、跨窗口重叠度阈值、扫描档位表与窗口数
  在发起扫描前固定并随批次落库；判据一旦落库，结果只能按该判据解释，改判据必须重跑，
  不允许事后重新解释已有批次。
- **所有产生回测的参数组合都必须计入试验次数台账**：搜索预算与多重检验预算同源，
  不提供“扫描不记账”的旁路。

## 2. 现状与缺口

已有基础（已逐条核对代码，结论：改造以“接缝补齐”为主，不是重构）：

- `FactorSpec.default_params`、策略 `factor_params` 和 `params_hash` 已为参数元数据、缓存隔离及
  回测复现留出基础。`index_factor_value` 已有 `params_hash` 列与
  `uq_index_factor_value_params` 部分唯一索引（`strategy_id IS NULL AND params_hash <> ''`），
  参数化因子值表这一层已经存在，不需要新表即可隔离参数变体。
- **计算器层已经参数化**：`MAComputer(period=…)`、`RSIComputer(period=…)`、`ATRComputer(period=…)`、
  `ReturnStdComputer(period=…)` 均以构造函数接收周期，`spec.factor_id` 按周期动态生成
  （如 `f"ma_{self._period}d"`）。缺的不是“能不能按参数算”，而是**注册表的实例工厂**与
  **策略层的实例身份**。
- **数值叶子扫描是通用实现**：`iter_numeric_leaves()` 递归收集任意路径的数值叶子，
  `build_knob_variants(config, max_knobs, knobs)` 支持 `--knobs` 显式旋钮清单。把因子实例参数
  接成旋钮可复用既有批次、队列和配置遍历框架，但必须新增由模板 schema 驱动的专用变体生成器；
  不能只扩展优先级表或复用通用 ±25% 扰动。
- `robustness scan` 已能对现有数值配置叶子做单旋钮邻域扫描，并输出 `is_plateau` 和 `reversal`；
  `domain/research/robustness.py::NeighborhoodResult` 是既有结构化返回类型。
- 生命周期服务已实行“健康状态系统计算、生命周期状态人工变更、系统不自动调参”的治理原则；
  研究期/验证期边界已由 `domain/research/periods.py::validate_backtest_period` 硬约束，
  LIVE 配置冻结已由 `StrategyConfigService` 实现。

现有缺口：

1. `factor_params` 目前仅接受注册因子的默认值；自定义参数由校验层拒绝（`params != spec.default_params`
   直接报“自定义参数暂未支持”）。
2. 回测预计算按固定 `factor_id` 从注册表取计算器（`FactorProvider` 用
   `c.spec.factor_id in factor_ids` 过滤，`FactorRegistry` 以 `factor_id` 为唯一 key），
   不能为 MA(6)、MA(37) 等动态参数实例化计算器——`MAComputer` 只在注册表构建时按
   `for period in (5, 10, 17, 20, 60)` 硬编码注册。
3. 单个 `factor_params.ma.period` 不能表达同一策略同时使用快慢两条均线（结构是
   `{factor_id: params}`，“一因子一参数”）。
4. 当前邻域扫描尚未把因子实例参数识别为专门的优化旋钮（优先级表中无因子参数档位），
   也不能输出连续参数区间的高原画像，`is_plateau` 只是布尔值 + 容差比较。
5. 线上生命周期模块未保存“上线时参数高原”的基准画像（`strategy_lifecycle` 只有
   `baseline_distribution` 分布分位表，健康快照只有 `metrics/diagnosis/recommended_action`），
   因而无法诊断高原收窄、偏移或消失。

6. **存量策略与证据不进入新架构**：稳健性变体与优化候选当前都是独立的 `strategy_config` 行
   （变体带 `is_variant=True`/`source_batch_id`，优化候选形如 `<基线 ID>__opt_<hash>`），
   策略列表页把它们当普通策略展示，`strategy_config.version` 又是可更新字段。因此"历史策略与
   历史回测"既不能作为台账的可靠来源，也不能作为新架构的迁移对象——本次升级只迁一条策略
   （见 5.5.1），并以它重建可信基线。

此外，**既有验收闸门存在已知的脆弱性，本方案必须先解决它，否则会把不稳定的判据升级成上线闸门**：

- `robustness scan` 的高原结论对扫描口径敏感。同一候选，`--preset quick`（2 窗口 / 8 旋钮）
  给出 `is_plateau=true`，换成 4 窗口扫描给出 `is_plateau=false`、`worse_ratio=0.75`
  （见 `docs/research/主线RS轮动v8/round3`、`round4`）。
- `_KNOB_PRIORITY` 把 `rebalance.` 排在最末，`quick` 预设（8 旋钮）**永远扫不到调仓日历相位**，
  而该旋钮已实测能造成约 10pct 的毛年化摆幅，因此验收清单缺“选股腿日程邻域”一项。
- `summary.neighborhood.is_plateau = null`（无有效变体）**不等于通过**，但现有描述容易被读成
  “没有发现问题”。
- 参数“高原”与“尖峰”的区分在项目内部已有反例：`docs/research/主线RS轮动v8/README.md` 记录
  “阈值 65/40 不是参数高原：在 4 组粗粒度备选里它是最好的一组，属于尖峰而非平台”。

## 3. 目标架构：因子模板与因子实例

### 3.1 设计原则

将“计算逻辑”与“策略内引用”分离：

| 概念 | 含义 | 示例 |
| --- | --- | --- |
| 因子模板 | 可版本化的计算逻辑 | `sma`、`return`、`rsi`、`atr` |
| 因子实例 | 一条策略内可被 score/filter/rank 引用的具名因子 | `ma_fast`、`ma_slow` |
| 参数空间 | 参数类型、范围、步长、候选档位、约束与回望规则 | `period: 5..250` |
| 参数指纹 | 模板版本与规范化参数的哈希 | `template_version + params_hash` |

策略配置新增 `factor_instances`。原有固定因子配置继续兼容，逐步迁移，不应破坏历史策略和历史回测。

```json
{
  "factor_instances": {
    "ma_fast": {
      "template_id": "sma",
      "params": {"period": 20}
    },
    "ma_slow": {
      "template_id": "sma",
      "params": {"period": 60}
    },
    "mom_medium": {
      "template_id": "return",
      "params": {"period": 40}
    }
  },
  "filters": {
    "logic": "AND",
    "rules": [
      {"factor": "ma_fast", "op": "gt", "compare_to": "ma_slow"}
    ]
  },
  "score": {
    "factors": {"mom_medium": 1.0},
    "scoring_mode": "rank"
  }
}
```

### 3.2 首批支持的模板

第一期只覆盖参数结构简单、数据依赖明确的指数级因子：

- `sma.period`：简单移动均线；
- `return.period`：区间收益/动量；
- `return_std.period`：区间收益标准差；
- `rsi.period`；
- `atr.period`。

复合面板因子、涉及多个窗口耦合的因子（如扩散、RRG）后续单独设计参数约束，不应随着第一期一并开放。

## 4. 参数空间与复杂度纪律

每个模板必须定义参数 schema、允许范围、候选网格、局部搜索步长、依赖约束和自然日回望规则。

以 `sma` 为例：

```json
{
  "template_id": "sma",
  "template_version": "1.0.0",
  "parameters": {
    "period": {
      "type": "integer",
      "min": 5,
      "max": 250,
      "research_grid": [20, 40, 60, 90, 120],
      "local_step": 5,
      "local_max_points": 9,
      "lookback_rule": "calendar_days(period * 1.75 + 10)"
    }
  }
}
```

档位表口径与项目方法论文档一致（`个人量化策略_过拟合与因子研究方法论.md` §5.3
“周期优先测试 20/40/60/90/120 等粗粒度值，**而不是 20～120 每个整数全部扫描**”）：

- `research_grid` 是**唯一**的粗筛档位表，用于识别候选高原；
- **档位数与覆盖跨度同时受约束**：档位数 **5～9 档**，且覆盖跨度（最大档位 − 最小档位）
  **≥ 合法值域跨度的 30%**。档位数下限是为了让 6.2 的“高原内至少 3 个连续档位”两侧
  仍留有非高原对照档位（5 档是同时满足这两件事的最小规模）；跨度下限是为了防止
  **缩小网格把窄高原洗白**——归一化宽度以网格覆盖跨度为分母，若网格可任意收窄，
  `[40, 60]` 这类 2 档窄网格会把任何区间都放大成近似 1.0。示例网格 `[20, 40, 60, 90, 120]`
  为 5 档、覆盖跨度 100，占合法值域跨度 245 的 41%，满足该约束；
- 同一策略的同一模板，**不得在两次扫描之间缩小网格后沿用旧批次结论**；网格属于判据快照
  （见 6.4），变更即需重跑；
- `local_step` 只在候选高原边界附近做局部扫描，默认 5 而非 1；
  **禁止** `local_step = 1` 的全区间逐点扫描；
- `local_max_points` 限制局部扫描点数（默认 9），与粗筛档位合计构成单模板单次扫描的
  试验次数上限（见第 7.1 节）；
- `min` / `max` 是合法值域（校验用），**不是搜索范围**——不提供值域内的任意参数穷举。

回望规则统一采用 `period * 1.75 + 10`（现有 `MAComputer` / `ATRComputer` / `ReturnStdComputer`
用的是 `period * 1.5 + 5`，`LowAmplitudeMomentumComputer` 用 `1.75 + 10`）。统一到更保守的
1.75 倍是刻意的：161 根有 OHLC 的 bar 在 A 股日历（春节 + 国庆叠加）上最多跨越 251 个自然日，
`1.5` 系数在大周期下余量会被摊薄。长周期模板的 `max` 需同时校验“研究期内可计算的样本数”，
避免出现像 MA250 这类在 2016 年起点上几乎无有效样本的档位。

优化遵循“两阶段、少旋钮”原则：

1. 先在具有经济含义的粗粒度网格（`research_grid`）上筛选；
2. 只在候选区域附近做小步长局部扫描，例如 MA35 至 MA55 按 5 档取
   `[35, 40, 45, 50, 55]`，而不是 35 至 55 逐日；
3. 默认一次只扫描一个因子参数；二维及以上联合扫描需要显式申请并记录额外试验次数；
4. 快慢均线等存在关系的参数须校验 `fast_period < slow_period`；同模板实例还应满足
   **最小间隔约束**（默认慢腿 ≥ 快腿 × 1.5），避免两条近似均线互相替代；
5. 限制一条策略中同模板的实例数量（默认上限 2，超出需显式申请并记录理由），
   防止堆叠高度相关的近似因子伪造出“宽高原”。

参数精度不应高于研究证据：若高原很宽，优先选择高原中心或易解释的整数档位，而不是表现最高的尖点。
**日频细扫只能用于定位高原边界，不能用于证明高原宽度**——相邻参数的回测结果高度相关，
其 Δ 差值不构成独立证据（见第 6.4 节）。

## 5. 引擎、缓存与复现改造

### 5.1 策略解析与校验

- `StrategyConfig` 新增 `factor_instances`，并允许评分、过滤、排序和择时模块引用实例 ID。
- 新增模板注册表及参数校验器；仅可引用已注册模板和合法参数组合。
- 旧 `factor_id` 保持可用。解析层将固定因子视为无参数或默认参数的兼容实例。
- 校验层需新增：同模板实例数量上限、`fast_period < slow_period` 等关系约束、
  参数值域（`min`/`max`）与档位表合法性、实例 ID 唯一性。
- 逐步废弃“`factor_params` 必须等于 `default_params`”的限制；在迁移完成前，不向旧结构直接开放任意自定义值。

**不可变策略修订与假设族**：现有 `strategy_config` 以 `strategy_id` 为主键，`version` 是可更新的
普通字段，不能承担“非退役策略修订”的引用、审计与清理职责。Phase 1 必须新增不可变的
`strategy_revision`（或等价命名）实体，至少包含 `revision_id`、`strategy_id`、`parent_revision_id`、
完整 `config_snapshot`、`config_hash`、`hypothesis_family_id`、`status`、`retired_at`、创建时间和审批
信息。LIVE 策略指向一个 revision；发布新参数只能创建新 revision，不能覆盖旧行。

**层次与兼容选择（Phase 0 拍板，本文档选定方案 C）**：`strategy_id` 与 `revision_id` 的关系必须
显式定义，否则迁移期无法兼容既有引用。三选一：

- 方案 A：一修订一 ID，`strategy_id` 即当前修订，靠 `parent_revision_id` 串链；
- 方案 B：策略族与修订分离，`strategy_id` 只作族标识，一切读路径按 `revision_id` 重写；
- **方案 C（本文档选定）**：`strategy_config.strategy_id` 保留为**策略族根**（对外稳定的 API 标识），
`strategy_revision` 作为其上的不可变修订链（`revision_id` 主键 + `strategy_id` 外键 +
`parent_revision_id` + `hypothesis_family_id`），`strategy_config` 增加 `live_revision_id` 指针。

**配置唯一写入口**：修订制启用后，`strategy_revision.config_snapshot` 是唯一可执行配置源；
`strategy_config` 只保留策略族的展示元数据、`live_revision_id` 与族级状态，原有
`strategy_config.config_json` 冻结为迁移兼容快照，不再被运行时、回测、优化或 API 更新路径读取。
`PUT /strategies/{strategy_id}`、优化 promote、草稿创建及所有内部写路径统一改为“创建新 revision
→ 通过校验与值就绪门禁 → 原子切换 `live_revision_id`”；禁止原地更新任意 revision 或
`strategy_config.config_json`。迁移完成后应在数据库权限/服务层双重拒绝对该字段的写入，避免旧 API
绕过不可变修订链。

选方案 C 的理由是迁移代价最小且不破坏既有证据链：全库有十余处 `strategy_id`（或
`candidate_strategy_id` / `strategy_a_id` / `strategy_b_id`）引用，分布在 `index_factor_value`、
`index_signal`、`research_run`、`research_run_item`、`backtest_run`、`backtest_comparison`、
`strategy_optimization`、`robustness_run`、`strategy_lifecycle`、`strategy_health_snapshot` 等表，
全部重写风险高；方案 C 让 `GET /strategies/{strategy_id}` 默认解析 `live_revision_id` 指向的修订，
旧引用可继续解析，而 `revision_id` 用于审计与精确引用。
**两种标识必须同时存在于 API 响应中**（`strategy_id` + `revision_id`），否则前端与报告无法区分
“同一策略族的不同修订”。

`hypothesis_family_id` 在提出经济假设时创建并不可变地贯穿父子 revision、稳健性变体、优化会话、
手工回测和因判据变化产生的重跑。同一假设族的 `n_trials` 永远累计；只有人工审批并在扫描前登记
“经济机制、资产池、信号定义均实质不同”的新假设，才可创建新的假设族。不得以新 revision、
复制策略、更改策略 ID 或删除历史记录作为台账重新起算的理由。

**历史 `validation_consumed_at` 的粒度**：该标记现在挂在 `strategy_config` 行上，语义是
“该策略首次消费验证期（2026-01-01 起）数据”。修订制下必须明确其归属，否则新建修订会让
“已消费验证期”的记录消失，等于冲掉 D-5 约束：

- `hypothesis_family_id` 是验证期消费的**唯一权威归属**，不随新建修订重置；
- 本方案规定一个 `strategy_id` 只能绑定一个不可变 `hypothesis_family_id`。若未来允许同一策略族
  承载多个经济假设，必须创建新的策略族，而不是在既有 `strategy_id` 下切换假设族；
- 任何修订消费验证期数据时，都在假设族级记录中追加一次记录（时间 + 来源 + 修订 ID）；
- 假设族级标记非空意味着该族已不再具备干净的样本外属性，此状态对族内所有修订生效，
  并在策略详情页显式展示。

**存量变体行与候选行的修订化（“因子中心重新注册 + 单策略迁移”下仍必须做）**：稳健性变体与
优化候选现在都是**独立的 `strategy_config` 行**（变体带 `is_variant=True` 与 `source_batch_id`；
优化候选以 `<基线 ID>__opt_<hash>` 命名并由 `strategy_optimization` 引用）。这正是"以复制策略
规避台账"的现实载体，因此即使只迁一条策略，也必须定义它们的归属规则：

- 变体行 / 候选行的 `hypothesis_family_id` 由其 `source_batch_id` 对应的
  `robustness_run.strategy_id`，或 `strategy_optimization.strategy_id` 反查确定；反查失败时
  拒绝迁移并报错，不得默认归入新族；
- 按 `source_batch_id` 批量清理变体的既有逻辑改为操作 `strategy_revision`，**清理修订不得
  连带删除 `robustness_run` / `strategy_optimization` 台账行**（否则等于删历史记录洗白 `n_trials`）；
- 本次迁移范围内（`mainline_rs_rotation_v12`）不需要转换历史变体行，但上述规则必须在 Phase 1
  落地，因为升级后的第一轮扫描就会产生新的变体与候选。

**迁移与日落条款**（缺了它，“逐步废弃”就无法验收）：

1. 解析层遇到 `factor_params`（无 `factor_instances`）时，按默认参数展开为等价实例，
   使旧配置与新结构走同一条执行路径；存在 `factor_instances` 时以新结构为准，
   两者同时出现且指向同一模板时报校验错误。
2. 提供迁移工具：把现有固定 MA 类因子（`ma_5d`/`ma_10d`/`ma_17d`/`ma_20d`/`ma_60d`）配置
   转换为等价 `factor_instances`，并比对转换前后回测指标完全一致。**本次作用于唯一迁移对象
   `mainline_rs_rotation_v12`**（其余策略不迁移，见 5.5.1），因此这里的回归就是 5.5.1 的
   迁移前后一致性回测，不另做批量策略回归。
3. 迁移工具就绪后，`factor_params` 转为**只读兼容层**（不再接受新增写入）；
   具体下线时间点由 Phase 0 决策记录确定，在此之前保持“仅接受默认值”。
4. 日落条款的验收条件：**迁移对象与后续新建的策略修订均不再使用 `factor_params`**，
   且迁移对象的等价实例已通过一致性回归（本次不要求清理未迁移的历史策略行——它们已按
   5.5.1 整体弃用）。

### 5.2 回测计算

`FactorProvider` 应根据策略引用的“模板 + 参数”动态生成计算器，而不是只按固定因子 ID 查注册表。

```text
ma_fast  -> SMAComputer(period=20)
ma_slow  -> SMAComputer(period=60)
```

回测和实时计算均以实际实例参数推导预热窗口。MA250、长周期动量等不得继续复用固定注册表中较短因子的最大回望期。

`FactorProvider` 现有的“按 `factor_id` 从注册表过滤计算器”（`c.spec.factor_id in factor_ids`）
需要扩展为“按 `(template_id, template_version, params)` 从模板工厂实例化计算器”，
并复用既有 `BatchFactorComputer.compute_batch()` 路径：模板工厂产出的一次性计算器实例
必须仍满足 `BatchFactorComputer` Protocol，否则扫描期会退化为逐点计算。

### 5.3 缓存与数据模型

**因子世代隔离**：`factor_definition` 与 `index_factor_value` 是全局共享资产，不能因为只迁一条策略
就清空或覆盖。新增不可变 `factor_generation_id`（或等价 generation 实体），模板、参数化实例、
因子值、值就绪记录和策略修订均显式关联世代；`mainline_rs_rotation_v12` 的新 revision 只引用新世代，
其余未迁移策略与历史回测继续以旧世代为**只读审计依据**。旧世代仅在所有引用它的策略修订和历史审计
需求均已退役、并完成可恢复归档后，才能整体清理。任何全局清表仅允许在全新数据库世代切换、停机和
完整备份均已获批准时执行——**本次单策略迁移不属于该场景**；若本次采用“新库只含新世代”的部署
路径，必须显式声明，并同步简化下面的世代承载与值表约束改造。该路径与“同库旧世代只读保留”
互斥：旧库必须作为只读审计数据源持续可访问，并在路由、前端与研究档案中明确旧策略、旧回测和
历史详情的读取来源；未完成旧库归档、访问权限和恢复演练前不得下线旧库。

**世代的定义与承载位置（Phase 0 必须拍板，实现前不得留白）**：先把“世代”的语义定死，否则迁移
代价无法估算。

- **世代是“因子定义集合的版本标签”**：一个世代包含一组模板定义、实例定义、参数 schema，
  并划定该世代下因子值的分区。同一时刻只有一个**活跃世代**（由目标策略修订的
  `factor_generation_id` 指向）；旧世代保留其定义与值行供历史审计与复算，但作为归档世代
  不再参与日频批算；同一 `factor_id`（或同一模板+参数）在新旧世代并存时，**以世代区分语义**，
  不得相互覆盖或跨世代读取。
- **承载位置二选一**（与 5.3 存储选址方案 A/B 联动，必须一起拍板）：

| | 位置 ①：命名规则承载 | 位置 ②：显式列承载 |
| --- | --- | --- |
| 做法 | 世代折叠进 `factor_id` 的合成命名规则，与 `template_version` 一起构成确定性的全局 `factor_id`（如 `ma_37d@gen2`） | `factor_id` 改可空，`factor_definition` / `index_factor_value` 显式增加 `factor_generation_id` 列 |
| 主键与外键 | `factor_definition.factor_id` 主键与外键**均无需改动** | `factor_definition` 主键改为复合键 `(factor_generation_id, factor_id)`，`FactorDefinitionRepository.find_by_id()` 签名随之变化，`index_factor_value.factor_id` 外键需重建为复合外键 |
| 值表唯一约束 | 两个部分唯一索引（`uq_index_factor_value_builtin` / `uq_index_factor_value_params`）**保持有效**——不同世代是不同 `factor_id`，不会撞键 | 两个部分唯一索引的键**必须加入世代列并重建**，否则跨世代写同一 `(trade_date, index_code, factor_id)` 会被唯一约束拒绝 |
| 代价 | 合成 ID 变长（需确认 `String(64)` 是否足够），且“同一个逻辑因子”在不同世代表现为两个 ID，跨世代比较需靠参数解析 | 结构最干净，但迁移与回滚面更大 |

- 本方案默认选择**位置 ①（命名规则承载）**：它与 5.3 方案 A 的 `factor_id` 合成命名、现有部分
  唯一索引、`init-factors` 同步策略完全相容，且不动主键与外键。选择位置 ② 必须在 Phase 0
  记入决策记录并说明迁移与回滚步骤。即使选择位置 ①，仍须保留 `factor_generation` 表，且
  `factor_definition` 增加普通 `factor_generation_id` 外键：字符串 ID 仅用于兼容现有主键/值表，
  generation 外键才是权威归属。解析策略修订时，所有引用的因子 ID 必须经定义表校验属于该 revision
  的 generation；不得通过切分 `@gen` 或正则猜测世代。

因子值的逻辑唯一键至少包括：

```text
factor_generation_id + trade_date + index_code + template_id + template_version + params_hash
```

注意这是**逻辑**键；在现有 `index_factor_value` 结构下如何承载，取决于上面的世代承载位置与下面的
存储选址决策（位置 ①/方案 A 把世代、`template_id`、`template_version` 折叠进 `factor_id` 的命名规则，
位置 ②/方案 B 落成独立列）。

`instance_id` 是策略配置语义，不属于跨策略可复用缓存键。通过参数哈希隔离 MA20、MA60 等变体，避免相互覆盖；相同模板版本和参数的多条策略可共用结果。

**存储选址决策（Phase 0 必须拍板，实现前不得留白）**：`index_factor_value.factor_id` 目前是
`ForeignKey("factor_definition.factor_id")` 且 `nullable=False`，而 `factor_definition` 由
`init-factors` 从代码 `FactorSpec` 同步。因此“以模板身份为缓存键”与“因子值表的外键约束”
存在张力，必须在下面两条中显式二选一：

- **方案 A（推荐，改动最小）**：参数化实例仍以 `factor_id` 落值表，`factor_id` 由
  `factor_generation_id` + `template_id` + `template_version` + 规范化参数按**确定性命名规则**生成
  （如 `ma_37d@gen2`），并在 `factor_definition` 中落一行合成定义（世代与模板身份被折叠进命名规则）。
  缓存身份 = `trade_date + index_code + factor_id + params_hash`。**前提是采用 5.3 的“位置 ①：命名
  规则承载”**：此时不同世代是不同 `factor_id`，现有两个部分唯一索引仍然有效，迁移只需加查询索引；
  若改用“位置 ②：显式列承载”，则两个部分唯一索引必须加入世代列并重建，方案 A 的“只需加查询索引”
  代价描述不再成立（详见上面的承载位置表）。为避免当前 `init-factors` 将“不在固定注册表中”的定义
  停用，`factor_definition` 必须增加来源/所有权标记（至少区分 `builtin` 与
  `parameterized_instance`）；同步服务只停用 `builtin` 来源中已从注册表删除的定义，
  参数化实例的有效性由世代、模板版本和被引用策略修订决定。扫描期不创建定义行。
- **方案 B（结构更干净，迁移更大）**：`factor_id` 改为可空，`index_factor_value` 显式增加
  `template_id` / `template_version` 列，重建两个部分唯一索引，并同步改造
  `IndexFactorValueRepository.bulk_upsert_params()`。

在补足上述来源/所有权语义后，方案 A 可复用现有 `params_hash` 部分唯一索引，且是 Phase 0 的
默认选择；选择方案 B 必须在 Phase 0 记入决策记录并说明迁移与回滚步骤。

**参数化 ID 规范**：示例 `ma_37d@gen2` 仅用于说明，不能作为通用拼接算法。真实 ID 必须由
canonical JSON 参数序列化 + 全量 `params_hash` 生成，格式为“可读模板短名 + 世代短名 + 模板版本短名
+ 固定长度哈希前缀”；完整参数与完整哈希仍存于定义行。生成器须确保长度不超过现有 `String(64)`，
并在短哈希发生碰撞时自动扩展前缀或拒绝写入，不能静默复用错误定义。

无论选哪条，`params_hash` 都继续作为“规范化参数（`sort_keys=True` 的 sha256）”的指纹，
`template_version` 承载公式/口径的版本化。**模板公式发生变化时必须提升 `template_version`**，
且只有“参数变化、结果等价”才允许保持同一版本。

**扫描期不落库（硬要求）**：参数扫描过程中产生的所有参数组合，其因子值一律通过内存批量预计算
获得（复用回测预计算路径），**不写入 `index_factor_value`**；只有最终候选配置所采用的参数组合
才持久化。理由：全池（数十个指数）× 数千交易日 × 数十个参数档位会产生数十万级行，
既污染因子值表，也会让“因子定义”表累积大量一次性合成行。此要求同时限制方案 A 的副作用。

数据库迁移需补齐对应唯一索引、查询索引和历史固定因子兼容映射。因子缺失诊断仍需保留
`FACTOR_UNKNOWN`、`NOT_COMPUTED`、`INSUFFICIENT_DATA` 三态语义。

**最终候选持久化的原子流程**：候选被人工接受后，必须在同一事务边界内完成
**元数据三元组**——“注册/激活参数化定义 → 创建值就绪记录（初始未就绪） → 写入可引用该定义的
新不可变策略修订”。任一步失败都应回滚，不能出现“策略修订已引用但定义缺失/未激活”的半成品。
这条约束的必要性有代码依据：
`StrategyConfigService` 校验因子时要求“存在且 `is_active=True`”，且 `FactorService.compute_and_store()`
用 `factor_definition` 的活跃行与注册表计算器**求交**（`active_ids & registry.all()`）才计算——
定义未激活时既不能通过策略校验，也不会被批算覆盖，且**不会报错**。

边界必须划在“元数据”上，**因子值本身不进入该事务**：值写入的量级是全池 × 全回望历史
（数十个指数 × 约 2430 个交易日 ≈ 十万级行），而本仓库是全同步 SQLAlchemy，把十万级 upsert
与元数据写入放进一个事务会产生长事务、锁等待与 WAL 膨胀。因此：

- 值就绪记录必须独立存储，逻辑唯一键为 `factor_generation_id + definition_id + params_hash +
  template_version + input_data_manifest_hash + data_as_of_date + universe_hash`，并含 `status`、覆盖交易日范围、
  覆盖指数池、完成时间、失败原因和任务 ID；
  不得仅在策略修订上存布尔值。`data_as_of_date` 或指数池变化后需产生新记录；
- **输入数据清单与 `market_data_generation` 的定义（必须写实，不能只留名字）**：
  - **按数据集类型分别维护，不是全局单值**——日线、指数估值、宏观指标、指数成分各自有独立的
    世代标识，因为它们的回填/修订时点互不相同，合成单一版本号会让“只有估值被回填”也触发
    全部因子重算；
  - **世代标识由“数据源 payload 版本 + 内容哈希（或已发布数据集版本号）”构成**，回填或修订
    同一交易日的历史数据即产生新世代；`ingested_at` 只能作辅助线索，不能直接当版本（重复摄取
    会改 `ingested_at` 而不改数据）；
  - 单个因子可能同时依赖日线、估值、宏观与成分数据，因此不得把多个数据集世代压成未定义的单值。
    **命名与语义必须统一**：`dataset_version` 指单个数据集类型（日线/估值/宏观/成分）的版本身份；
    `generation_id` 是该身份在 manifest 中的字段值（`dataset_key -> generation_id`）；
    每次计算生成 canonical `input_data_manifest`，其 `input_data_manifest_hash` 是值就绪键与
    回测快照中的**权威输入版本身份**；完整清单随记录保存，不得只存哈希；
  - **它与 `data_as_of_date` 是两个正交维度**：`data_as_of_date` 是“算到哪一天”，
    `input_data_manifest` 是“这一天之前的每种数据各用哪一版”。两者任一变化都要产生新的值就绪记录；
  - 落库位置与粒度、以及“新数据集版本何时取代旧版本成为默认输入”，在 Phase 0 一并拍板；
- **就绪判定必须做区间与池的子集校验**：记录只有在“覆盖区间 ⊇ 引用修订的回测/运行区间”且
  “覆盖指数池 ⊇ 该修订的 point-in-time 指数池”时才判就绪。`data_as_of_date` 早于修订区间末端，
  或只覆盖当前活跃指数的记录，一律判未就绪、不得复用——否则用今天的记录跑历史区间会在
  “当时存在、现已退市”的指数上缺值；
- 值就绪记录为“未就绪”时，策略修订**不得**被判为可运行；
- 因子值走**幂等补算**（按 `factor_id + params_hash`，同一身份重复写入结果一致），
  由既有后台任务队列异步执行；
- 值缺失时引擎必须返回既有的 `NOT_COMPUTED` 语义，而不是 `FACTOR_UNKNOWN`
  （“已注册但当日未算”与“因子不存在”的治理含义完全不同，前者可补算、后者是配置错误）。

**定义行的生命周期与活跃世代**：定义是否可被历史修订解析，与是否参与当前日频批算是两种不同
语义，不能继续共用 `is_active`。方案 A 引入的 `parameterized_instance` 定义行需新增
`definition_enabled`（可被修订解析/审计）和 `compute_enabled`（允许日频批算）两个状态；
现有 `is_active` 在迁移后仅作兼容显示，并由二者派生。世代也必须纳入同一套成本规则：

- 只要仍有**至少一个非退役策略修订**引用该定义，就保持 `definition_enabled=True`；无任何引用后
  软停用为 `definition_enabled=False`，但保留历史因子值、定义与外键关联；
- **只有活跃世代且 `compute_enabled=True` 的定义参与日频批算**。归档世代即使仍被历史修订引用，
  也保持 `definition_enabled=True`、`compute_enabled=False`，从而既可审计又不产生每日计算成本；
- 这条是硬要求而非优化：`FactorDefinitionRepository.find_active()`
  是无世代过滤的全量查询，`FactorService.compute_and_store()` 取的正是它
  （`active_ids = {d.factor_id for d in self._repo.find_active()}`），因此不加世代过滤就会
  **同时为两个世代重复计算**。Phase 1 必须让该查询按活跃世代和 `compute_enabled` 过滤；
- 这条规则必须挂在既有的清理路径上。原因是 `compute_and_store()` 无条件遍历所有活跃定义，
  每一行残留都会变成**每日永久计算成本**——双门控里的 `active_ids` 是全量拉取，没有策略维度过滤。

### 5.4 可复现性

每个回测、稳健性批次、优化会话和上线修订应固化：

- 完整策略配置及每个实例的模板、版本、参数和参数哈希；
- **完整的 `input_data_manifest`（`dataset_key -> generation_id`）及其 `input_data_manifest_hash`**、
  各数据集的数据源 payload 版本与数据截止日（`data_as_of_date`）——不得只存哈希，否则快照无法
  自证用的是哪一版数据；
- `factor_generation_id`；
- 实际预热期；
- 日历来源、执行模型、换手模型、成本口径等既有运行指纹；
- 因子模板升级前后的兼容映射。

模板公式发生变化时必须提升模板版本；历史回测必须按其快照所引用的版本解释或明确标记为不可复算，不能静默使用新公式覆盖历史结论。市场日线、估值、成分或宏观数据被回填/修订时，
新的 `input_data_manifest_hash` 必须变化；无法取得同一输入清单时，结果只能标记为
“配置可复现、数据版本不可复现”，不得宣称逐日结果可复现。

### 5.5 数据迁移与前端适配

本次升级采用**最小迁移**：只把 `mainline_rs_rotation_v12` 迁到新架构，其余策略、草稿变体与
历史回测数据不复用；因子中心按新身份建立**独立世代**。这样可以把迁移风险压到一条策略上，
代价是必须把“重新建立可信基线”这件事本身做成有证据的动作。

**5.5.1 迁移范围与基线重建**

- 本方案正文统一使用 **`mainline_rs_rotation_v12`** 指代本次迁移对象。研究档案
  （`docs/research/主线RS轮动v8/round4`）记录的被测策略为 `mainline_rs_rotation_v11`（v2.2.0，
  `config_hash` 前缀 `7b196bcf…`），候选为 `mainline_rs_rotation_v11__opt_45f75866`（v2.3.0）——
  **落地前必须先在库中核实本次要迁的 v12 对应的真实 `strategy_id`、`version` 与 `config_hash`，
  并以库中实际值回填本方案与研究文档**，不得凭研究档案的命名推断，避免出现“文档说 v12、
  库里叫 v11”的错位；
- **迁移前先固化基线证据**：在旧架构上跑一次全区间回测（同一执行模型、同一成本口径、
  2016-01-01～2025-12-31），保存逐日收益序列、指标摘要与 `config_hash`，作为迁移比对的基准；
- **只迁一条策略**：其余 `strategy_config` 行、`is_variant=True` 的变体行、`__opt_` 候选行
  与历史 `backtest_run` 一律不迁移，直接弃用；
- **策略标识沿用、不重命名**：迁移后策略族标识保持与研究档案和既有证据一致；
  若需改名，必须同步回填研究文档并说明理由，不得只改库中 ID；
- **迁移前后一致性回测（验收硬要求）**：用同一执行模型、同一成本口径、同一区间
  （2016-01-01～2025-12-31）在迁移前后各跑一次全区间回测，要求逐日收益序列完全一致
  （差异为零）。这是本方案唯一能证明“新架构没有改变计算口径”的证据，缺失则迁移不可验收。
  **该比对必须固定在同一 `input_data_manifest`（即同一 `input_data_manifest_hash`）内**：若两次
  回测之间日线、估值、宏观或成分数据发生过回填/修订，差异就不再是迁移引起的，此时必须先恢复到
  同一数据快照重跑，否则不得据该比对判定迁移通过；
- **台账起算点不得默认归零**：本次迁移是架构升级，不是新的经济假设。迁移前该策略及其可识别
  父策略/候选的历史试验，尽管不足以复用为新架构的绩效证据，仍须形成保守的
  去重后的 `historical_trial_lower_bound` 并计入新 `hypothesis_family_id` 的 `n_trials`；计数来源、无法识别的
  范围和估计方法必须写入决策记录。若历史试验无法可靠计数，则该假设族在完成预先登记的新研究样本前
  **不得以 Deflated Sharpe 通过上线接受闸门**，而不是把 `n_trials` 记为 0。迁移完成后的所有扫描、
  重跑、变体与候选，一律按第 7.2 节继续累计。**推导口径写实**（避免“保守下界”停留在形容词）：
  - 先为可识别记录构造 `trial_identity = hypothesis_family_id + config_hash + research_period +
    execution_fingerprint`，再按该身份去重；同一配置的重复回测、`robustness_run.trial_count`、
    优化会话和 `is_variant=True` / `__opt_` 行若指向同一身份，只计一次，符合第 7.2 节的定义；
  - 无法关联到 `trial_identity` 的历史来源不并入“下界”，而单列为 `unknown_trial_penalty`：它是
    保守惩罚而非可证明下界，必须同时展示其来源与数量，并纳入 Deflated Sharpe 的有效试验数；
  - **`unknown_trial_penalty` 的取值规则（必须量化，不能留白）**：它直接决定该族能否过闸
    （DSR 对 `n_trials` 是对数敏感），因此不允许实现者自取数值：
    - 取值 = **可识别下界的保守倍率**（默认 `2 × historical_trial_lower_bound`，且不低于
      “该族历史分轮数 × 每轮典型扫描变体数”的估算值）；倍率与估算依据写入决策记录；
    - 若可识别部分本身残缺（例如分轮扫描走本地 `research batch` 未落库，连分轮数与每轮
      变体数都无法估算），则该惩罚值不可量化，此时**该族不得以 Deflated Sharpe 过闸**，
      与上文“无法可靠计数”的兜底一致；
    - 预期后果要在文档层面讲明：按 `docs/research/主线RS轮动v8` 的记录，单轮 4 窗口扫描约
      29 个变体、分 4 轮累计，叠加保守倍率后 `n_trials` 很可能一次性被推到数百量级，
      DSR 门槛随之显著抬高——这是本机制的预期效果，不是缺陷；
  - **族边界必须显式登记**：哪些 `strategy_id` 视为同一假设族（例如按 `mainline_rs_rotation_v1*`
    前缀归并）必须在决策记录中列名并给出证据，不得靠前缀匹配隐式推断；
  - 已知缺口必须写明：研究档案显示部分分轮扫描走本地 `research batch`（不落库），
    因此可识别部分**可能远小于真实试验数**；该事实写入决策记录，作为“必要时不得以
    Deflated Sharpe 过闸”的触发依据；

**5.5.2 因子中心新世代注册**

- **不复用历史定义行，但不清空全局表**：为新 `factor_generation_id` 建立新的模板、实例定义与
  因子值；旧 `factor_definition` / `index_factor_value` 行保留在旧世代，用途**仅限历史审计与

  `definition_enabled=True` + `compute_enabled=False`（可审计、不计算），避免把历史
  `parameterized_instance` 语义带进新架构，也避免每日重复计算（见 5.3 的活跃世代规则）；
- **注册内容升级**：新表/新接口必须能表达模板与实例的区分，`factor_definition` 至少要有
  来源/所有权标记（`builtin` / `template` / `parameterized_instance`，见 5.3），并能携带
  参数 schema（值域、`research_grid`、`local_step`、`lookback_rule`）而不仅是默认值；
- **新世代建立后必须验证计算口径未变**：以 `mainline_rs_rotation_v12` 为唯一验证载体，重建前后
  因子值抽样比对（同一指数、同一交易日、同一参数），差异为零；这条与 5.5.1 的回测一致性
  互为印证——回测一致但因子值不一致、或反之，都说明迁移有问题。
  **该抽样比对同样必须固定在同一 `input_data_manifest`（即同一 `input_data_manifest_hash`）内**
  （理由同上）。

## 6. 参数高原分析

### 6.1 定义与输出

参数高原不是“收益最高的一点”，而是在连续参数区间内，风险收益表现、交易特征和滚动窗口结果均相对稳定的区域。

**宽度以粗筛档位数衡量，不以参数单位衡量。** 在日频 1 步长下，MA35 与 MA55 是近乎同一个模型，
“宽度 21”是扫描粒度的构造产物而非证据；因此高原宽度必须按 `research_grid` 的档位计。

扫描 `ma_fast.params.period` 的粗筛档位 `[20, 40, 60, 90, 120]` 并对候选区做局部扫描后，
结果应能够描述（示例为结构示意，数值须由真实批次产生）：

```text
候选高原档位：[40, 60, 90]
建议参数：60
有效档位数：3
归一化宽度：0.50      # 区间跨度 50 / 当次粗筛网格覆盖跨度 100
区间中位夏普：0.82
区间最差夏普：0.71
最大回撤范围：-18.4% 至 -21.0%
滚动窗口重叠度：0.74
有效独立档位数：2     # 按相邻档位相关性折算，见 6.3
局部细扫边界：35 / 105（仅用于定位边界，不作为宽度证据）
结论：高原成立
```

输出必须是结构化对象，而不是 `is_plateau` 布尔值：连续档位区间、中心点、归一化宽度、
有效档位数、有效独立档位数、区间内分布（中位/最差）、风险与成本指标区间、
跨窗口重叠度、以及**每一条未通过判据的具名原因**。

### 6.2 高原判定的可计算判据

全部判据必须同时成立才判定“高原成立”；任一条不成立都要在输出里给出具名原因。

| 判据 | 阈值 / 口径 | 与既有机制的关系 |
| --- | --- | --- |
| 连续档位数 | 区间内至少 **3 个有效评估档位**（缺数据/缺行情的档位不计入，并说明被剔除的档位） | 复用 `is_plateau=null` 的“无有效变体”语义，不得当通过 |
| 归一化宽度 | 区间跨度 / **当次粗筛网格覆盖跨度** **≥ 0.15**；网格覆盖跨度为最大档位减最小档位，并受 4 章的档位数与跨度下限约束 | 新增；防止把单点最优读成高原。合法值域仅用于校验，不作为分母 |
| 区间内主指标落差 | 区间内最差档位相对峰值的差距 **≤ 容差**，容差取自配置 `ROBUSTNESS_TOLERANCE`（默认 0.1 夏普），**扫描前冻结、禁止事后调整** | 复用既有容差设置，但补上“区间内最差档位”而非“全部变体” |
| 风险与交易特征 | 最大回撤、换手率、空仓率、持仓集中度逐项按 `variant_risk_acceptance` 判定；每项必须冻结比较统计量、基线参照、劣化方向、容忍量、最小样本和缺失处理；**任一项因样本不足而无法计算时整体判不成立**（与 6.5 同一传播规则），不得跳过该项 | 新增策略级验收快照；不可直接复用 `build_baseline_distribution`（实测其仅含 `period`/`sample_days`/`drawdown_pct`/`sharpe_full_period`/`windows[].{excess_return_pct, sharpe_ratio}`，没有换手率、空仓率、持仓集中度） |
| 跨窗口重叠度 | 多个滚动窗口各自判定的高原区间，两两重叠率 **≥ 0.6** | 新增；窗口数随扫描预设固定 |
| 成本/池/消融 | 成本压力、候选池扰动、因子消融后高原依然成立 | 复用既有稳健性变体族 |
| 方向反转 | 存在 `reversal`（最好变体明显优于基线且最差变体明显劣于基线）则**直接否决** | 复用既有 `reversal` |
| 样本边界 | 高原贴近研究期起点或终点、由单一年份或单一行情段驱动，则判不成立 | 新增；复用分段一致性口径 |

### 6.3 统计力要求（防止把自相关当稳健性）

相邻参数档位的回测结果高度相关，其 Δ 差值不构成独立证据。因此：

1. 不得用细粒度扫描（`local_step` 小于粗筛档距）得到的平滑曲线来证明高原宽度；
2. 应计算**有效独立档位数** `n_eff`，口径固定如下（样本取**全 `research_grid` 档位**，
   而不是仅高原内档位——只取高原内时 `n_eff` 会退化成“档位数”的同义指标，与 6.2 的
   “至少 3 个有效档位”重复；取全网格才能度量“整条曲线是否只是高相似度造成的平滑”这一
   正交问题，其中高原外的对照档位是必要样本）：

   - 对每个滚动研究窗口，取该窗口内各档位的日策略收益率序列，按共同交易日对齐后
     构造档位 × 档位的 Pearson 相关矩阵 `R`；
   - 以 `R` 的特征值 `lambda_i` 计算参与率 `n_eff = (Σ lambda_i)^2 / Σ(lambda_i^2)`；
   - 任一窗口的有效共同交易日少于**判据快照中的最小共同交易日数 `min_common_days`**、
     相关矩阵不可计算或出现非有限值时，**该窗口判“证据不足”**。
     `min_common_days` 不在文档中写死（默认建议 120 而非 60：5～9 档的相关矩阵在 60 天
     样本上估计噪声过大，而本节对各窗口取 `min`，对噪声尤其敏感），由 Phase 0 与
     `min_effective_rank` 一并校准后冻结；
   - 各窗口取最小 `n_eff`，低于判据快照中的 `min_effective_rank` 时高原不成立；
     `min_effective_rank` 不预设为固定值，必须由 Phase 0 在既有研究策略语料上回放校准后冻结：
     记录 `n_eff` 分布及其与滚动样本外表现的关系，并在决策记录中写明阈值与依据；
   - **校准语料不足时的处置**：本次升级的语料只有 `mainline_rs_rotation_v12` 一条策略及其
     扫描批次，样本量很可能不足以支撑分布校准。若回放无法给出有依据的阈值，则
     `n_eff` **只作报告项、不进上线接受闸门**，并在决策记录中写明“语料不足、未校准”的结论
     与后续补校条件；不得为了“能用”而随手取一个整数充当阈值；
   - 计算所使用的日历、窗口划分、共同样本对齐与缺失值剔除规则、`min_common_days` 与
     `min_effective_rank`、公式本身，全部进入判据快照；
   - 同时报告跨滚动窗口的**档位排序一致性**作为辅助证据；
3. 低波动、低换手的策略在细粒度扫描下天然产生平滑曲线，**平滑不等于稳健**——
   必须用粗筛档位间的落差作为宽度证据。

### 6.4 判据快照的冻结与预设敏感性

高原结论对扫描口径敏感，这已是项目内的已知事实（`docs/research/主线RS轮动v8`：同一候选
`--preset quick` 给出 `is_plateau=true`，4 窗口扫描给出 `is_plateau=false`）。因此：

- 容差、窗口数、档位表、覆盖率门槛、主指标、`variant_risk_acceptance`、`min_common_days`、
  `min_effective_rank` 及其校准依据
  构成一个**判据快照**，扫描前固化并随批次落库；
- 判据快照变化后，历史批次**不得重新解释**，必须重跑；
- 前端与报告必须显示本批次采用的判据快照，禁止只显示 `is_plateau` 布尔值；
- 不允许“换个预设就通过验收”——验收引用批次时必须同时匹配配置哈希与判据快照。

### 6.5 判据传播规则（证据不足一律不成立）

统计力证据不可比较时，**不得跳过、只能否决**：

- 任意滚动研究窗口判“证据不足”（有效共同交易日不足快照下限、相关矩阵不可计算或出现非有限值）时，
  整体结论即为“证据不足”，高原不成立；**不允许**剔除该窗口后对其余窗口取 `min`；
- 判据快照中的任一项因数据不足而无法计算时，同样判不成立，并在输出中给出具名原因。
  **适用范围包括 `variant_risk_acceptance` 的每一个子项**——某项样本不足时不得跳过该项、
  只判定其余子项通过；
- 本节与第 7.3 节“`is_plateau = null` 一律不视为通过”是同一条原则，
  实现时必须共用同一判定出口，避免两处各写一套传播规则。

## 7. 搜索预算与试验次数纪律

参数空间一放开，最大的风险不是算不出来，而是**多重检验预算被悄悄透支**。本节为独立硬约束。

### 7.1 搜索预算

- 每轮研究必须**事先声明**搜索预算：扫描哪些实例参数、用哪张档位表、局部扫描点数上限；
- 默认一次只扫一个因子实例参数；二维及以上联合扫描须显式申请并记录额外试验次数；
- 单模板单次扫描的试验次数上限（ceiling）= 粗筛档位数（5～9）+ 局部扫描点数（≤9），
  实际次数按声明的档位表计算并落库；
- 超出预算的扫描不得启动。

### 7.2 试验次数台账

- **一次试验 = 一个新的参数组合（配置哈希）被执行了一次回测**；同一配置重复运行只计一次；
- 稳健性批次经 `robustness_run.trial_count` 落库；优化会话经已评估会话数计入；
- 因子实例参数的**粗筛与局部扫描都必须计入**台账（两者都消耗多重检验预算）；
- `Deflated Sharpe` 的 `n_trials` 取台账值（`robustness` 变体数 + `optimization` 已评估会话数），
  手工不入批次的对比必须显式补充 `--n-trials`；
- 禁止在方案之外手写循环产生未入账的候选；
- **台账单调递增，重跑不给豁免**：判据快照变更导致的重跑同样是已经做过的试验，照样入账。
  因此“研究做得越认真、N 越大、Deflated Sharpe 越难过”是这套机制的预期行为而不是缺陷。
  但必须为它配一个显式出口，否则该门会变成不可解除的死锁：
  - 同一 `hypothesis_family_id` 内不得重置台账；可选处置只有继续按既有台账研究，或接受该门失败并
    放弃候选，不得更换口径重试；
  - 只有在人工审批并于扫描前登记“经济机制、资产池、信号定义均实质不同”的新经济假设时，才可
    创建新的 `hypothesis_family_id` 与新台账起算点；新策略修订、复制策略、调参或更换报告名称均不构成
    新假设；
  - **不得**通过清空/回填 `robustness_run`、删除优化会话或新建同假设策略来压低 `n_trials`；
  - 台账达到门槛后仍继续扫描时，系统应提示“继续扫描将进一步提高通过门槛”。

### 7.3 与既有机制的衔接

`robustness scan` 应复用既有批次、队列、取消、覆盖率与试验次数台账机制。
`is_plateau = null`（无有效变体）与 `n_variants` 不足门槛的情形**一律不视为通过**。
优化验收应拒绝仅有单点最优、邻域反转或高原证据不足的候选。

## 8. 优化器与稳健性扫描接入

### 8.1 可优化旋钮清单

将以下路径视为可选优化旋钮，并接入既有 `iter_numeric_leaves()` + `--knobs` 机制：

```text
factor_instances.ma_fast.params.period
factor_instances.ma_slow.params.period
factor_instances.mom_medium.params.period
```

上面三个路径只是**示例，不是白名单**。清单的通用形式是：

```text
factor_instances.<任意实例 ID>.params.<该模板 schema 声明的参数名>
```

实例 ID 由策略自定义，因此实现时必须以“实例参数”这一**语义类别**接入扫描器
（取值必须落在扫描前冻结的 `research_grid` 内、并满足模板的值域与关系约束），
不能把示例路径硬编码成清单，否则漏掉其他实例时不会报错、只会静默不扫。

因子参数不能复用通用 `_knob_values()` 的约 ±25% 扰动规则。扫描器必须按模板参数 schema
专用生成变体：粗筛严格使用扫描前冻结的 `research_grid`；局部扫描只从冻结的边界、`local_step`
与 `local_max_points` 派生。通用数值叶子扫描仍用于权重、阈值等非模板参数，但不得越过模板参数
的值域、关系约束和搜索预算。

清单必须同时纳入**项目已实测的脆弱旋钮**，否则高原闸门会被日程相位之类的旋钮绕过：

```text
rebalance.selection.frequency / day_of_week / week_parity / day_of_month   # 选股腿日程
rebalance.risk.frequency / day_of_week / week_parity / day_of_month        # 风险腿日程
```

`_KNOB_PRIORITY` 目前把 `rebalance.` 排在最末，导致 `--preset quick`（8 旋钮）永远扫不到日程相位；
必须把**调仓日历类旋钮的优先级提到与择时阈值同级**，或在验收清单中单列“选股腿日程邻域”一项。
两件事至少做一件，并同步冻结扫描口径（见 6.4）。

### 8.2 优化流程

```text
提出经济假设
  -> 声明搜索预算与判据快照
  -> 粗粒度档位扫描（research_grid）
  -> 识别候选高原
  -> 局部参数扫描（仅定位边界）
  -> 滚动样本外、成本、池扰动、消融验证
  -> 选择高原中心参数
  -> 生成候选策略修订
  -> 人工审核、发布或拒绝
```

流程中每一箭头都产生可落库证据；判据快照与试验次数随批次固化，供事后审计复核。

## 9. 上线后治理：监测而非自动调参

上线时，将通过研究期证据得到的高原画像（档位区间、中心点、归一化宽度、判据快照、
有效独立档位数）固化到策略生命周期记录中，与既有 `baseline_distribution` 并列。
系统可定期计算以下诊断：

| 诊断 | 含义 | 判定口径 | 系统动作 |
| --- | --- | --- | --- |
| 高原收窄 | 原本稳健的连续区间明显变小 | 监控期诊断扫描的归一化宽度或有效档位数低于基线画像 | 标记关注，建议人工复核 |
| 高原偏移 | 稳健区中心出现迁移迹象 | 中心点位置相对基线画像的偏移超过预设档距 | 记录漂移预警，不输出新参数方向 |
| 高原消失 | 相邻参数普遍恶化或方向强烈反转 | 监控期诊断扫描判定高原不成立，或出现 `reversal` | 提升风险等级，建议暂停扩张或复核 |

诊断口径必须与 6.2 的判据共用同一实现与同一判据快照，避免“研究期判成立、监控期判消失”
的口径不一致。监控期诊断扫描的试验次数同样计入台账（见 7.2）——监控本身也在消耗多重检验预算：
诊断扫描发生在 LIVE 之后，其试验次数必须计入**该 LIVE 修订所属 `hypothesis_family_id` 的台账**
（而不是新建一个族或不计），否则“监控也消耗预算”这句话在实现上无落点。
诊断只可陈述偏移、收窄或消失的事实，不能据此给出候选参数、候选研究范围或推广方向；这些方向
属于新的研究制度，必须在预先定义的滚动研究与盲置验证流程中独立产生。

线上闭环为：

```text
生产参数（例如 MA40）
  -> 监测表现、回撤、换手、信号和高原画像
  -> 发现收窄、偏移或消失
  -> 生成诊断与复核建议
  -> 人工发起研究、审核候选新版本
  -> 新版本上线，并保留旧版本与全部证据
```

验证/监控数据只能用于发现风险、否决或提出复核。不得根据短期表现自动从 MA40 切换到 MA65，也不得以验证数据循环寻优后把新参数当作确认结论。

若未来需要使用新的历史阶段再次开展研究，必须另行建立版本化的滚动研究、盲置验证与发布审批制度；不能隐式改变当前研究期/验证期边界。

## 11. 验收标准

- 同一策略可同时引用 MA20 与 MA60，且均可使用任意受支持窗口；
- MA(6)、MA(37) 等合法实例无需新建 Python 固定因子 ID 即可被回测；
- 参数值域之外的取值、超限的实例数量、违反 `fast_period < slow_period` 与最小间隔的配置被校验拒绝；
- 相同模板的不同参数不会在实时或回测缓存中相互污染；
- **参数扫描期不向 `index_factor_value` 写入任何参数组合的因子值**，仅最终候选参数落库；
- 历史回测可由策略快照、模板版本、参数哈希和运行口径复现；
- 固定因子与等价参数实例的迁移前后回测指标逐日一致（误差为零）；
- 参数扫描输出的高原画像包含档位区间、归一化宽度、有效档位数、有效独立档位数、
  跨窗口重叠度与具名未通过原因，**不是**单个布尔值或最高点；
- `n_eff` 阈值在既有研究策略语料回放后冻结，并保留校准证据；未校准不得作为上线接受闸门；
  语料不足时按 6.3 判为“只报告、不进闸门”，且该结论本身写入决策记录；
- **单策略迁移与基线重建**：`mainline_rs_rotation_v12` 的迁移前后全区间回测（同执行模型、
  同成本口径、2016-01-01～2025-12-31）逐日收益完全一致，差异为零；**比对固定在同一
  `input_data_manifest_hash` 内**（数据发生回填/修订时须先恢复同一数据快照重跑）；
  其余策略与历史回测已按 5.5.1 弃用，不残留仍被引用的孤儿记录；
- **台账下界与惩罚入账证据**：`historical_trial_lower_bound` 与 `unknown_trial_penalty` 均已计入
  该 `hypothesis_family_id` 的有效试验数，并在决策记录中给出计数来源、去重身份口径
  （`trial_identity`）、惩罚取值规则与倍率、族边界登记（视为同族的 `strategy_id` 清单及证据）、
  无法识别范围与估计方法；惩罚不可量化时，该族未完成预先登记的新研究样本前不得以
  Deflated Sharpe 过闸；
- **因子中心新世代注册**：新世代 `factor_definition` 含来源标记
  （`builtin`/`template`/`parameterized_instance`）与参数 schema；新旧世代因子值抽样
  （同指数、同交易日、同参数、**同一 `input_data_manifest_hash`**）差异为零，
  且旧世代未被清空或覆盖；
- **活跃世代隔离**：日频批算只处理活跃世代且 `compute_enabled=True` 的定义
  （`find_active()` / `compute_and_store()` 按世代与计算开关过滤，**过滤在 SQL WHERE 条件中完成**，
  不是全量拉取后内存筛除）；归档世代保持 `definition_enabled=True`、`compute_enabled=False`，
  可审计但不产生计算成本；同一逻辑因子在新旧世代并存时不互相覆盖、不跨世代读取；
- **输入数据清单落库**：回测与值就绪记录均保存**完整 `input_data_manifest`**
  （`dataset_key -> generation_id`，各数据集版本独立维护）及其 `input_data_manifest_hash` 与数据截止日；
  无法取得相同输入清单时，输出明确标记为“配置可复现、数据版本不可复现”，不得宣称逐日结果可复现；
- **摄取侧内容哈希**：每个数据集的内容哈希（或已发布数据集版本号）在摄取时计算并落库，
  是 `input_data_manifest` 中 `generation_id` 的唯一来源；不得用 `ingested_at` 代替内容版本；
- **配置唯一写入口**：`strategy_config.config_json` 冻结后，任何 API、优化 promote、草稿创建或
  内部写路径都无法原地修改它；发布新参数只能创建新修订并原子切换 `live_revision_id`；
  数据库权限与服务层双重拒绝生效；
- **前端适配**：因子中心能区分模板与实例并展示参数、策略页能展示 `revision_id` 与父修订链、
  回测页能按修订筛选、变体与候选不再出现在策略列表、生命周期页能展示高原画像；
  上述任一能力仅在 API 可用而界面缺失，视为本阶段未完成；
- `is_plateau = null`（无有效变体）与 `n_variants` 不足门槛一律不视为通过；
- **判据传播**：任一窗口、任一判据（**含 `variant_risk_acceptance` 的每一子项**）“证据不足”时
  整体判不成立，实现中不存在“剔除该窗口/该项后重算”的分支；
- 判据快照随批次落库；判据变化后必须重跑，历史批次不得重新解释；
- `research_grid` 满足档位数 5～9 与覆盖跨度 ≥ 合法值域 30% 的约束，且窄于下限的网格被校验拒绝；
- 每次扫描的粗筛与局部扫描次数均计入试验次数台账，`n_trials_breakdown` 可完整还原；
- **候选持久化原子性**：不存在“策略修订已引用参数化实例、但定义未激活或值就绪记录缺失”的状态；
  异步补算未完成时引擎返回 `NOT_COMPUTED` 而非 `FACTOR_UNKNOWN`；
- **值就绪记录粒度**：记录以因子世代、定义、参数哈希、模板版本、`input_data_manifest_hash`、
  数据截止日和指数池身份唯一确定；
  就绪判定对引用修订的区间与 point-in-time 指数池做子集校验，覆盖范围不足或仅覆盖当前活跃
  指数的记录不得复用；
- **定义行生命周期**：定义状态按双状态表达——无任何非退役策略修订引用时置
  `compute_enabled=False`，是否同时 `definition_enabled=False` 取决于是否仍有历史修订需要解析；
  归档世代恒为 `definition_enabled=True` + `compute_enabled=False`（可审计、不计算）；
  历史回测重算依据其修订快照直接从模板工厂实例化，不依赖活跃定义列表；`is_active` 仅作兼容显示；
- **试验次数不可洗白**：同一 `hypothesis_family_id` 的所有修订、扫描和重跑累计 `n_trials`；
  新修订、复制策略或更改策略 ID 不能重置台账，新假设必须有扫描前审批记录；
  清理变体修订不得连带删除 `robustness_run` / `strategy_optimization` 台账行；
- **验证期消费的族级语义**：`validation_consumed_at` 以假设族为唯一权威归属；本方案中策略族与
  假设族一对一，新建修订不重置，且族级标记对族内所有修订生效；
- **实时侧覆盖**：参数化实例进入日频批算路径（`compute_and_store` 能从活跃定义行派生计算器），
  且其活跃定义行不会在 `init-factors` 同步时被误停用；
- 优化验收拒绝邻域反转、尖峰最优或高原证据不足的候选；
- 高原漂移只能触发诊断与人工复核，绝不会自动更改 LIVE 策略参数；监控期诊断扫描的试验次数
  计入该 LIVE 修订所属假设族台账；
- 所有研究、扫描、候选版本、审批与发布过程可回溯。
