# 回测流程问题与优化清单

本文记录 2026-09-13 对 `mainline_rs_rotation_v8` 做白板复盘与优化时**实际撞到**的问题，
以及从这些问题里提炼出的回测流程可优化点。每条都带现场证据；已修复的标注修复位置，
未修复的给出建议与优先级。

背景工程记录见 [`docs/research/主线RS轮动v8/README.md`](../research/主线RS轮动v8/README.md)。

优先级：**P0** 会直接产出错误结论；**P1** 严重影响可用性/吞吐；**P2** 效率与体验。

---

## A. 已修复（本轮改动，均有回归测试）

### A-1 [P0] `robustness scan` 浅拷贝别名导致整批变体失效

- 现象：`robustness scan --strategy mainline_rs_rotation_v8` 直接失败并返回
  `{"error": "未派生任何有效变体（候选配置均未通过校验）"}`。
- 根因：`build_knob_variants()` 用 `dict(config)` **浅拷贝**，再通过 `_set_leaf()` 就地下标写值
  （`services/robustness_service.py:890` 与 `:1061`）。v8 配置里 `risk.max_portfolio_exposure=1`
  按"整数"档位规则被扰动成 `2`（越界），这个越界值因为共享嵌套字典而**泄漏到全部候选乃至基线
  config 对象**，于是 33 个变体全部校验失败；同时 `baseline_config_hash` 是在污染之后计算的，
  落库的基线指纹也是错的。
- 修复：`create()`、`build_knob_variants()`、`build_ablation_variants()` 全部改为 `deepcopy`；
  新增 3 个回归测试（不得改写输入配置、单个越界档位不得泄漏、消融同样不得就地改写）。
- 影响面：任何"数值叶子中有越界扰动"的策略都会踩到，属于静默失效（只报一句笼统错误）。

### A-2 [P0] 负整数阈值被抬成正数

- 现象：`filters.rules[i].value = -5`（`return_5d > -5`）的邻域扰动产生 `+1` 而不是 `-6`。
- 根因：`_knob_values()` 对所有 int 一律 `step = max(1, ...)`、再 `max(1, value - step)`
  （`services/robustness_service.py:1016`），把"周期/持仓数至少为 1"的规则错误地套到了
  可以是负数的阈值上。
- 修复：负数整数阈值按 `value ± step` 扰动，不再抬到正数；测试覆盖 `{-6, -4}`。

### A-3 [P1] 列表内数值从未参与扰动

- 现象：v8 的过滤阈值（`filters.rules[2].value`）在稳健性扫描里从未出现，"阈值是不是平台"
  无从检验。
- 根因：`iter_numeric_leaves()` 不遍历 list 节点（`services/robustness_service.py:982`），
  而 `_set_leaf()` 也只支持点号路径，遇到 `rules[2]` 会抛 `KeyError` 并被静默跳过。
- 修复：`iter_numeric_leaves()` 支持列表下标（`filters.rules[2].value`），`_set_leaf()` 增加
  `name[index]` 解析（`_split_index`）。

## B. 队列与执行吞吐（未修复，优先级最高）

### B-1 [P1] 服务端并发跑回测反而比串行慢 20 倍

- 现象：稳健性批次入队后（scan 136 + pool 44 + ablate 36 + 对照组 15 ≈ 231 条回测），
  队列吞吐长期停在 **0.3~0.7 条/分钟**；4 个 running 任务的已耗时超过 6 分钟仍未结束。
  同一时段用 CLI 同步跑一条 2 年回测只要 **17 秒**（空闲时 1 年回测 8 秒）。
- 证据：`background_job` 4 running 的 `started_at` 推算耗时 > 6 分钟；
  `pg_stat_activity` 显示 4 个会话卡在 `Lock/transactionid` 与 `Client/ClientRead`，本机 CPU 占用
  仅 0~3%（说明不是本机算力瓶颈）。
- 判断：`JobQueue` 在**单进程内开 4 个线程**（`infra/job_queue/queue.py`），回测是 CPU + 数据库
  混合型任务，线程并发既拿不到 GIL 收益，又把 4 份数据库负载叠加在一起，结果单条变慢、
  总吞吐下降。
- 建议：回测类任务改为**独立 worker 进程**（`uvicorn --workers N` 或单独的 worker 服务），
  并把并发度绑定到"数据库能承受的并发"这一容量参数；先在空载下测量单条耗时随并发度的
  曲线，再决定默认并发。

### B-2 [P1] 队列没有优先级 / 取消 / 暂停

- 现象：一次长批次会把后续所有任务排在队尾。本轮为了等 5 条候选复核回测，只能改用
  CLI 同步执行绕开队列（同步模式不经过队列）。
- 建议：`enqueue(..., priority=)` 已在仓储层存在但 CLI 未暴露；补充
  `backtest run --priority`、`backtest cancel <id|batch>`、`robustness cancel <batch>`，
  并允许把批次整体暂停。

### B-3 [P1] 队列与单条回测的耗时不可观测

- 现象：判断"卡住了还是在跑"只能手工连库查 `pg_stat_activity`、`background_job`。
- 建议：`GET /backtests` 暴露 `queued_seconds` / `elapsed_seconds` / 队列位置；
  `GET /runs` 或新增 `/queue/stats` 给出按类型的积压与吞吐。

### B-4 [P2] `GET /backtests` 不支持状态过滤

- 现象：`limit=200` 的一条查询结果全是 `pending`，看不到已完成记录。
- 建议：增加 `status` / `strategy_id` / `purpose` / 时间范围过滤。

### B-5 [P1] 应用时间戳与数据库 `now()` 时区混用

- 现象：用 SQL 计算 `now() - started_at` 得到 8 小时误差（应用写 UTC 的 naive 时间戳，
  `now()` 返回会话本地时间 = UTC+8）。本轮诊断里差点据此误判"任务卡了 8 小时"。
- 建议：`backtest_run.started_at/finished_at`、`background_job.*` 等列统一 `timestamptz`
  （或统一在 SQL 侧用 `now() at time zone 'utc'`）；前端展示层再做时区转换。

### B-6 [P2] 外部数据摄取与回测争抢同一个远程库

- 现象：本轮吞吐崩塌期间，`pg_stat_activity` 里持续出现 `INSERT INTO stock_moneyflow`、
  `INSERT INTO stock_daily_close`、`SELECT DISTINCT ... stock_daily_basic` 等个股摄取语句，
  与回测会话互相拖慢。
- 建议：给回测保留并发预算（连接池/限流），或把批量数据摄取安排在回测之外的时间窗；
  长期看数据摄取与回测最好分离实例。

### B-7 [P1] 卡死的 running 任务会永久阻塞批次汇总

- 现象：`ablate` 批次 35/36 成功、`pool` 批次 43/44 成功，各有一条回测长期停留在
  `running`（同一时段其它回测正常完成，队列整体在推进）；`robustness collect` 要求整批
  完成，于是官方汇总迟迟拿不到。
- 现场：`backtest_run` 中 `ef250c62-8965-4a7e-841a-50514f030ba7`（基线 2016-01-04~2018-06-28）
  与 `afc54a73-8aa1-4641-9b63-ecae5a172997`（消融变体 2020-12-25~2023-06-29）已 `running`
  **61.8 分钟**，而同时段其它同长度窗口的扫描变体只要 0.3~0.7 分钟。
- 根因：`recover_stuck_jobs()` 只在进程启动时执行一次，运行期没有心跳、没有单任务超时、
  没有僵尸任务扫描；一条卡住的回测会一直占用 worker，并让整个批次无法收口。
- 建议：① `background_job` 增加 `heartbeat_at`，worker 周期性更新，扫描线程把超时任务
  重置为 pending 或 failed；② `robustness collect --allow-partial` 支持"跳过缺失窗口并
  标记 coverage"（本次即需要该能力）；③ 回测循环内部已有"每 100 天 checkpoint 提交"，
  可以把最后一次提交时间作为活性信号。

## C. 回测口径与结果可信度

### C-1 [P0] 周度调仓的交易日历静默降级，会产生两套结果

- 现象：同一配置在平台与"按真实交易日历复现"的本地引擎上，2022-2023 段累计收益差 1.2pp、
  2024-2025 段差 2.5pp，且差异全部集中在**长假后第一周**。
- 根因：`DefaultRebalanceScheduler` 在交易日历不可用时降级为 `WeekendFallbackCalendar`
  （`domain/strategies/rebalance.py:58`、`domain/common/trading_calendar.py:40`），
  只按星期判断交易日。于是"目标星期（周三）恰好是法定节假日"的那一周，会把节假日当成交易日，
  导致整周跳过调仓（实测 2022-05-05 之后、2025-01-02 之后各有若干天）。
- 影响：结果不可复现地依赖"当时 akshare 是否可用"；降级只写一条 warning 日志，回测结果里
  **没有任何痕迹**——同一 `config_hash` 的两条回测可能代表两种调仓日历。这与系统反复强调的
  "消除口径分叉"原则冲突。
- 建议：① 回测启动前强校验交易日历可用，不可用则拒绝或 fail-fast；② 若必须降级，
  在 `backtest_run.warnings` 写入结构化 `CALENDAR_FALLBACK` 提示并标记该回测"口径降级"；
  ③ 把 `calendar_source` 纳入 `stability` 口径指纹。

### C-2 [P1] 换手率不计清仓 / 建仓腿

- 现象：调仓日 `prev` 或 `new` 为空时换手记为 0（`services/backtest_service.py:799`
  `if prev_positions and new_positions`）。v8 在 2016-2017 段有 13 天属于"清仓型调仓"，
  其换手成本被系统性记为 0。
- 影响：净口径指标低估成本，方向上偏向"高换手策略"。
- 建议：统一按 `Σ|Δw| / 2` 计入（含清仓与建仓腿），或在 `stability` 里并列给出两种口径。

### C-3 [P1] 净口径成本档位必须重跑回测

- 现象：`params["_cost_bps"]` 在创建回测时固化，想看 20bp/30bp/50bp 只能新建回测
  （或像本轮一样自己读逐日序列重算）。
- 建议：`GET /backtests/{id}` 支持 `?cost_bps=` 覆盖（读取路径现算，零额外成本），
  并在 `stability` 里同时给出多档净口径。

### C-4 [P1] 分段回测缺少官方"拼接全期"口径

- 现象：规则要求总跨度 > 5 年必须分段，但分段之后没有把各段日收益串成全期指标/净值的接口；
  本轮只能自己按日期拼接（`analyze_costs.py --aggregate`）。
- 建议：新增 `backtest merge --segments id1,id2,...`（校验区间连续、口径一致后拼接），
  或在 `optimization show` 中直接给出拼接全期指标。

### C-5 [P2] 删除回测记录会留下悬挂引用

- 现象：用户清空 `backtest_run` 后，`robustness_run.variants[].backtest_ids`、
  `strategy_optimization`（42 行）、`strategy_lifecycle.research_backtest_id`（1 行指向已删除回测）
  都指向不存在的回测。
- 建议：删除时联动标记/软删除，或对上述字段加外键与 `ON DELETE SET NULL`；
  稳健性/优化/生命周期详情页对悬挂引用给出显式提示。

### C-6 [P2] 回测产物缺少"有效候选池"的时间线

- 现象：v8 的 21 个池成员里，`000688` 2016-2019 完全无行情、`931160`/`931743` 2016-2017
  无行情，`930601`/`931152`/`931494` 早期缺开盘价（T+1 开盘执行不可用）；回测只在
  `warnings` 里给一条汇总提示，看不出"早期实际可交易池只有 13~16 个"。
- 建议：`stability` 输出"逐日有效候选池规模"序列与"因数据缺失被剔除的指数—日期区间"。

## D. 研究流程与工具链

### D-1 [P1] 缺少"批量变体 → 秒级评估"的官方路径

- 现象：探索性诊断（消融 9 个 + 池扰动 9 个 + 参数 15 个 + 简化 6 个 ≈ 40 个变体 × 5 段）
  在平台上等于 200 条回测，在当前吞吐下需要数小时；本轮只能在研究目录里复刻引擎
  （`v8_local.py`，换手/仓位与平台完全一致、收益差 < 1pp）才把成本压到秒级。
- 建议：把 `domain/` 的纯函数评估能力暴露成离线批量工具
  （如 `cli research batch --variants variants.json --segments ...`，可选不落库），
  或提供"轻量回测"模式：跳过逐日结果落库、只返回汇总指标 + 稳定性块。

### D-2 [P1] `robustness scan` 的默认规模与实际吞吐不匹配

- 现象：默认 `--max-knobs 30` × `--windows 4` = 136 条回测；更糟的是截断按**路径字母序**，
  默认 30 档时 `timing.thresholds.*`（最可疑的拟合参数）永远排在最后被截掉。
- 建议：① 支持"关键旋钮清单"（配置里标注 `scan_priority` 或显式 `--knobs`）；
  ② 提供 `--windows 2 --max-knobs 8` 的"轻量体检"预设并把它写进验收清单；
  ③ 截断顺序改为按业务重要性而非字母序。

### D-3 [P2] 稳健性结果没有进入前端

- 现象：`robustness` 只有 CLI + 只读 API，页面上看不到 PBO/DSR/邻域结论，
  人工复核要开终端。
- 建议：策略详情页增加"稳健性"页签（批次列表、邻域Δ分布、消融边际贡献、PBO/DSR）。

### D-4 [P2] 稳健性变体策略的清理没有元数据支撑

- 现象：一次 scan 会批量创建 `<base>__rbXXXX_*` 形式的 draft 策略（本轮 33 个），
  清理时只能按 ID 前缀猜。
- 建议：`strategy_config` 增加 `source_batch_id` / `is_variant` 字段（或复用
  `description` 里的批次号建立索引），并提供 `strategy prune-variants --batch <id>`。

### D-5 [P2] 验证期留痕只覆盖回测，不覆盖"研究者的眼睛"

- 现象：v8 的历史版本说明显示 v1.4~v1.6 都在 2010-2026 全区间（含 2026 验证期）上选参数，
  但 `backtests/validation-usage` 只能列出"跑过验证期回测"的记录，无法标记
  "该策略的验证期已被消费"这一状态。
- 建议：在 `strategy_lifecycle` 或策略元数据上增加 `validation_consumed_at` /
  `validation_consumed_note`，一旦查看过验证期结果即标记，后续该策略的验证期证据只能用于否决。

## E. 本轮实际操作中值得保留的做法

1. **先对齐再分析**：本地复现必须先与平台逐段对齐（换手/仓位完全一致、收益差 < 1pp）
   才允许用来下结论；对齐过程本身就是发现 C-1 的方式。
2. **分段 + 拼接**：研究期切成 5 个两年段，先看逐段再拼接全期，避免单次长区间掩盖阶段差异。
3. **成本四档并列**：毛 / 10bp / 20bp / 30bp / 50bp 一起看，换手 13 倍的策略只看毛口径会得出
   相反结论。
4. **区分"探索"与"验收"**：探索用本地引擎（秒级、可跑几十个变体），验收用平台回测
   （正式口径、落库可审计）。
5. **同步 CLI 作为队列的旁路**：队列积压时用 `backtest run`（默认同步）绕开队列，
   单条 17 秒即可拿到正式口径结果。
