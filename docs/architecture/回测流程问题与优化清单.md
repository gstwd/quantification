# 回测流程问题与优化清单

本文记录 2026-09-13 对 `mainline_rs_rotation_v8` 做白板复盘与优化时**实际撞到**的问题，
以及从这些问题里提炼出的回测流程可优化点。每条都带现场证据；已修复的标注修复位置，
未修复的给出建议与优先级。

**修复进度**：A 类（P0/P1 口径与校验）、B 类（队列与执行吞吐）、C 类
（回测口径与结果可信度）与 D 类（研究流程与工具链）已全部修复，
修复实现与回归测试见各条目下的"修复"小节。

背景工程记录见 [`docs/research/主线RS轮动v8/README.md`](../research/主线RS轮动v8/README.md)。

优先级：**P0** 会直接产出错误结论；**P1** 严重影响可用性/吞吐；**P2** 效率与体验。

## A. 已修复（本轮改动，均有回归测试）

### A-1 [P0] `robustness scan` 浅拷贝别名导致整批变体失效

- 现象：`robustness scan --strategy mainline_rs_rotation_v8` 直接失败并返回
  `{"error": "未派生任何有效变体（候选配置均未通过校验）"}`。
- 根因：`build_knob_variants()` 用 `dict(config)` **浅拷贝**，再通过 `_set_leaf()` 就地下标写值
  （`services/robustness_service.py:890` 与 `:1061`）。v8 配置里 `risk.max_portfolio_exposure=1`
  按"整数"档位规则被扰动成 `2`（越界），这个越界值因为共享嵌套字典而**泄漏到全部候选乃至基线
  config 对象**，于是 33 个变体全部校验失败；同时 `baseline_config_hash` 是在污染之后计算的，
  落库的基线指纹也是错的。
- 修复：`create()`、`build_knob_variants()`、`build_ablation_variants()` 全部改为 `deepcopy`；
  新增 3 个回归测试（不得改写输入配置、单个越界档位不得泄漏、消融同样不得就地改写）。
- 影响面：任何"数值叶子中有越界扰动"的策略都会踩到，属于静默失效（只报一句笼统错误）。

### A-2 [P0] 负整数阈值被抬成正数

- 现象：`filters.rules[i].value = -5`（`return_5d > -5`）的邻域扰动产生 `+1` 而不是 `-6`。
- 根因：`_knob_values()` 对所有 int 一律 `step = max(1, ...)`、再 `max(1, value - step)`
  （`services/robustness_service.py:1016`），把"周期/持仓数至少为 1"的规则错误地套到了
  可以是负数的阈值上。
- 修复：负数整数阈值按 `value ± step` 扰动，不再抬到正数；测试覆盖 `{-6, -4}`。

### A-3 [P1] 列表内数值从未参与扰动

- 现象：v8 的过滤阈值（`filters.rules[2].value`）在稳健性扫描里从未出现，"阈值是不是平台"
  无从检验。
- 根因：`iter_numeric_leaves()` 不遍历 list 节点（`services/robustness_service.py:982`），
  而 `_set_leaf()` 也只支持点号路径，遇到 `rules[2]` 会抛 `KeyError` 并被静默跳过。
- 修复：`iter_numeric_leaves()` 支持列表下标（`filters.rules[2].value`），`_set_leaf()` 增加
  `name[index]` 解析（`_split_index`）。

## B. 队列与执行吞吐（已修复，2026-09-14）

> 修复实现集中在 `infra/job_queue/`（lane 并发预算、心跳、协作取消、僵尸扫描）、
> `api/routers/queue.py`（队列观测）、`api/routers/backtests.py` + `services/backtest_service.py`
> （状态过滤、排队可观测、取消）、`services/robustness_service.py`（批次取消/暂停、部分汇总）、
> 迁移 `0046_queue_observability`（timestamptz + 队列元数据）。
> 回归测试：`tests/unit/test_job_queue.py`、`tests/unit/test_robustness_control.py`。

### B-1 [P1] 服务端并发跑回测反而比串行慢 20 倍

- 现象：稳健性批次入队后（scan 136 + pool 44 + ablate 36 + 对照组 15 ≈ 231 条回测），
  队列吞吐长期停在 **0.3~0.7 条/分钟**；4 个 running 任务的已耗时超过 6 分钟仍未结束。
  同一时段用 CLI 同步跑一条 2 年回测只要 **17 秒**（空闲时 1 年回测 8 秒）。
- 证据：`background_job` 4 running 的 `started_at` 推算耗时 > 6 分钟；
  `pg_stat_activity` 显示 4 个会话卡在 `Lock/transactionid` 与 `Client/ClientRead`，本机 CPU 占用
  仅 0~3%（说明不是本机算力瓶颈）。
- 判断：`JobQueue` 在**单进程内开 4 个线程**（`infra/job_queue/queue.py`），回测是 CPU + 数据库
  混合型任务，线程并发既拿不到 GIL 收益，又把 4 份数据库负载叠加在一起，结果单条变慢、
  总吞吐下降。
- 修复：
  - 队列按 lane 划分，回测类任务（`backtest`/`comparison`）独占 **回测 lane**，与摄取/因子等
    通用任务互不抢占 worker（B6 的并发预算隔离一并解决）；
  - 回测 lane 并发默认 **1（串行）**：`QUANT_ETF_JOB_QUEUE_BACKTEST_WORKERS`；通用 lane
    `QUANT_ETF_JOB_QUEUE_WORKERS` 默认由 4 降到 **2**（同一台的数据库连接预算）；
  - 支持**独立 worker 进程**：`QUANT_ETF_JOB_QUEUE_EMBEDDED=false` 让 API 只入队，
    再用 `python -m quant_etf_api.worker`（或 `cli queue worker`）单独消费，容量独立可调。

### B-2 [P1] 队列没有优先级 / 取消 / 暂停

- 现象：一次长批次会把后续所有任务排在队尾。本轮为了等 5 条候选复核回测，只能改用
  CLI 同步执行绕开队列（同步模式不经过队列）。
- 修复：
  - 优先级：`backtest run --priority N`、`robustness scan/ablate/pool --priority N`
    （`background_job.priority` 早已在认领排序中使用，现已在 CLI 暴露）；
  - 取消：`backtest cancel <id>`（`POST /backtests/{id}/cancel`）、
    `robustness cancel <batch>`（`POST /robustness/{id}/cancel`）。未开始的任务直接落
    `cancelled`；运行中的任务只打 `cancel_requested` 标记，由回测主循环在安全检查点
    （每日循环起点，取消标记有 5 秒 TTL 缓存）协作退出，已提交的日结果保留；
  - 暂停：`robustness pause/resume <batch>`（`POST /robustness/{id}/pause|resume`），
    pending → paused → pending，暂停期间不被认领；
  - 批次号写入 `background_job.batch_id`，稳健性批次与优化会话的回测任务都能整批控制。

### B-3 [P1] 队列与单条回测的耗时不可观测

- 现象：判断"卡住了还是在跑"只能手工连库查 `pg_stat_activity`、`background_job`。
- 修复：
  - 新增 `GET /api/queue/stats`（积压/吞吐/运行中任务/并发预算）与
    `GET /api/queue/jobs`（任务明细，含心跳时间与已耗时），CLI 对应
    `cli queue stats|jobs`；
  - `GET /backtests` 每条回测附带 `job_status` / `queued_seconds` / `elapsed_seconds` /
    `queue_position` / `job_priority` / `batch_id`（回测任务统一去重键
    `backtest:{id}`，据此反查队列任务）；
  - 前端：回测中心新增"队列"列与取消按钮，运行记录页新增队列概览面板。

### B-4 [P2] `GET /backtests` 不支持状态过滤

- 现象：`limit=200` 的一条查询结果全是 `pending`，看不到已完成记录。
- 修复：`GET /backtests` 新增 `status` / `purpose` / `order_by`(created_at|started_at|
  finished_at) / `descending` 参数（`strategy_id`、`created_from/to` 原有），CLI 对应
  `backtest list --status/--purpose/--order-by/--asc/--limit`；前端回测中心新增状态与
  用途下拉筛选。

### B-5 [P1] 应用时间戳与数据库 `now()` 时区混用

- 现象：用 SQL 计算 `now() - started_at` 得到 8 小时误差（应用写 UTC 的 naive 时间戳，
  `now()` 返回会话本地时间 = UTC+8）。本轮诊断里差点据此误判"任务卡了 8 小时"。
- 修复：迁移 `0046_queue_observability` 把 `background_job.*`、
  `backtest_run.created_at/started_at/finished_at`、
  `backtest_comparison.created_at/started_at/finished_at` 统一改为 `timestamptz`
  （存量 naive 值按 `AT TIME ZONE 'UTC'` 解释），应用侧统一用
  `infra.time.utcnow_aware()` 写入 aware UTC；回测列表按中国日期过滤时也改为传 aware
  下界。前端仍按北京时间展示。

### B-6 [P2] 外部数据摄取与回测争抢同一个远程库

- 现象：本轮吞吐崩塌期间，`pg_stat_activity` 里持续出现 `INSERT INTO stock_moneyflow`、
  `INSERT INTO stock_daily_close`、`SELECT DISTINCT ... stock_daily_basic` 等个股摄取语句，
  与回测会话互相拖慢。
- 修复：随 B-1 的 lane 隔离一并落地——回测 lane 的并发即"回测可用的数据库并发预算"
  （默认 1 条），摄取/因子等任务在通用 lane，两者不再叠加；独立 worker 进程部署时
  还能把两者放到不同进程/不同容量配置，必要时进一步分离实例。

### B-7 [P1] 卡死的 running 任务会永久阻塞批次汇总

- 现象：`ablate` 批次 35/36 成功、`pool` 批次 43/44 成功，各有一条回测长期停留在
  `running`（同一时段其它回测正常完成，队列整体在推进）；`robustness collect` 要求整批
  完成，于是官方汇总迟迟拿不到。
- 现场：`backtest_run` 中 `ef250c62-8965-4a7e-841a-50514f030ba7`（基线 2016-01-04~2018-06-28）
  与 `afc54a73-8aa1-4641-9b63-ecae5a172997`（消融变体 2020-12-25~2023-06-29）已 `running`
  **61.8 分钟**，而同时段其它同长度窗口的扫描变体只要 0.3~0.7 分钟。
- 根因：`recover_stuck_jobs()` 只在进程启动时执行一次，运行期没有心跳、没有单任务超时、
  没有僵尸任务扫描；一条卡住的回测会一直占用 worker，并让整个批次无法收口。
- 修复：
  - `background_job.heartbeat_at`：worker 执行期每 15 秒写一次心跳
    （`QUANT_ETF_JOB_HEARTBEAT_INTERVAL_SECONDS`）；
  - 运行期僵尸扫描线程（`QUANT_ETF_JOB_ZOMBIE_SCAN_ENABLED`）：把心跳超过
    `QUANT_ETF_JOB_STUCK_TIMEOUT_SECONDS`（默认 1800 秒）未更新的任务回收；
    即使心跳正常，运行超过 `QUANT_ETF_JOB_MAX_RUNTIME_SECONDS`（默认 7200 秒）的长任务
    同样回收，覆盖"卡在数据库锁上"的场景；
  - 回收时回调 `JOB_ABANDON_HANDLERS`，把对应 `backtest_run` / `backtest_comparison`
    一并落为 failed（附 `JOB_ABANDONED` 结构化提示），批次因此可以收口；
  - `robustness collect --allow-partial`：跳过未完成/失败窗口，按已完成窗口汇总，并把
    `coverage`（expected/completed/pending/failed/is_partial）写入 summary，批次状态落
    `partial`；`cancel` 会把批次内任务已被取消、永远不会再跑的 pending 回测直接落为
    cancelled，运行中的回测则走协作取消路径（主循环退出后自行落 cancelled）。
- 验证：现场那两条卡死回测已被扫描回收（`scan_zombies` 回收 2 条），ablate 批次用
  `--allow-partial` 汇总得到 `coverage={expected:36, completed:35, failed:1}`、状态 `partial`。

### C-1 [P0] 周度调仓的交易日历静默降级，会产生两套结果

- 现象：同一配置在平台与"按真实交易日历复现"的本地引擎上，2022-2023 段累计收益差 1.2pp、
  2024-2025 段差 2.5pp，且差异全部集中在**长假后第一周**。
- 根因：`DefaultRebalanceScheduler` 在交易日历不可用时降级为 `WeekendFallbackCalendar`
  （`domain/strategies/rebalance.py:58`、`domain/common/trading_calendar.py:40`），
  只按星期判断交易日。于是"目标星期（周三）恰好是法定节假日"的那一周，会把节假日当成交易日，
  导致整周跳过调仓（实测 2022-05-05 之后、2025-01-02 之后各有若干天）。
  更关键的是：`BacktestService.__init__` 与 `StrategyDecisionService` 构造调度器时
  **根本没有注入日历**，所以回测恒定跑在周末近似日历上。
- 影响：结果不可复现地依赖"当时 akshare 是否可用"；降级只写一条 warning 日志，回测结果里
  **没有任何痕迹**——同一 `config_hash` 的两条回测可能代表两种调仓日历。
- 修复（严格口径，不再有任何近似路径）：
  - **彻底删除 `WeekendFallbackCalendar`**；`TradingCalendar` 的
    `is_trading_day` / `latest_trading_day` / `next_trading_day` / `trading_days_between`
    在取不到日历时一律抛 `TradingCalendarUnavailableError`（消息含修复指引）；
  - 日历解析统一走 `resolve_trading_calendar(db, required_range=...)`：
    **上游数据源（Tushare 优先 → AkShare）→ 本地 `trading_calendar` 表快照 → 报错**，
    两种来源都是真实日历，不是按星期推算；
  - `DefaultRebalanceScheduler(trading_calendar)` 日历改为**必填位置参数**，
    并删除"日历异常时降级为按星期比较"的 `except` 分支；
  - 回测侧：周度/月度调仓解析失败 → 回测直接落 `failed`；每日调仓与日历无关，
    指纹记为 `not_required`；来源写入 `params["_calendar_source"]`（`upstream` / `database`
    / `not_required`）并透出到 `stability.calendar_source`，使用本地快照时给出
    `CALENDAR_SOURCE_DATABASE` 信息级提示；
  - 上游加载失败只做 **60 秒** 负缓存，避免一次瞬时网络故障把日历冻结一整天；
  - 调用点按三类语义处理：后台任务/CLI **上抛落失败**、调度器线程**拒绝本次执行并记错误**、
    HTTP 读端点返回 **503**（`GET /system/data-quality`、`GET /ai-factors/previous-trading-day`、
    策略分配等；显式传 `trade_date` 可绕过日历）；
  - 新增审计入口：`GET /backtests?calendar_source=`、`cli backtest list --calendar-source`，
    用于找出"跑在另一种日历口径上"的存量回测。
- 验证：`tests/unit/test_trading_calendar_strict.py`（优先级、抛错、负缓存、无降级类）、
  `tests/unit/test_rebalance_calendar.py`（指纹、fail-fast、提示）、
  `tests/unit/test_calendar_http_errors.py`（503）。现场实测：新回测的
  `stability.calendar_source` 为 `upstream`（AkShare 可用时）或 `database`
  （上游不可用时回退本地 8797 行日历快照，并带 `CALENDAR_SOURCE_DATABASE` 提示），
  `grep -rn "WeekendFallbackCalendar" apps/` 已无结果。

### C-2 [P1] 换手率不计清仓 / 建仓腿

- 现象：调仓日 `prev` 或 `new` 为空时换手记为 0（`services/backtest_service.py:799`
  `if prev_positions and new_positions`）。v8 在 2016-2017 段有 13 天属于"清仓型调仓"，
  其换手成本被系统性记为 0。
- 影响：净口径指标低估成本，方向上偏向"高换手策略"。
- 修复：
  - 调仓日统一按 `Σ|Δw| / 2` 计入（`domain/portfolio/turnover.py::compute_turnover`），
    删除主循环里的"一侧为空则记 0"守卫；建仓腿与清仓腿全额入账；
  - 新增换手口径指纹：新回测写 `params["_turnover_model"] = delta_w_v2`，
    存量回测读取时标注为 `legacy_v1`（`stability.turnover_model`），前端对 legacy
    显示"历史换手口径，净口径需重跑后可比"。
- 验证：`tests/unit/test_backtest_turnover.py`（清仓/建仓日换手落库、指纹）、
  `tests/unit/test_domain_layering.py::test_compute_turnover_includes_open_close_legs`。
  现场实测：新回测 `stability.turnover_model == "delta_w_v2"`，存量 243 条回测
  全部读为 `legacy_v1`（前端会提示净口径需重跑后可比）。

### C-3 [P1] 净口径成本档位必须重跑回测

- 现象：`params["_cost_bps"]` 在创建回测时固化，想看 20bp/30bp/50bp 只能新建回测
  （或像本轮一样自己读逐日序列重算）。
- 修复：
  - `domain/research/stability.py::compute_cost_ladder`：只重算与成本有关的量
    （成本序列、累计/年化/夏普/超额），不重算年集中度/分段/回撤 → O(档位数 × 交易日数)，
    读取路径零可感额外成本；
  - `stability.cost_ladder` 始终并列输出系统配置的档位（默认 `0/10/20/30/50`，
    0 = 毛口径），档位由 `QUANT_ETF_STABILITY_COST_LADDER` 配置；
  - `GET /backtests/{id}?cost_bps=` 与 `cli backtest show --cost-bps/--cost-ladder`
    可按需覆盖主口径与档位，**不落库、不重跑**。
- 验证：`tests/unit/test_research_stability.py::TestCostLadder`、
  `tests/unit/test_backtest_turnover.py::test_ladder_zero_bp_equals_gross`。
  现场实测：`backtest show <id> --cost-ladder 0,10,50` 输出三档；`0bp` 档净累计
  与 `metrics.cumulative_return_pct` 一致；`?cost_bps=50` 覆盖后的
  `stability.net_annualized_return_pct` 与 50bp 档位值**完全相等**（并同步进
  `metrics.net_*`）。

### C-4 [P1] 分段回测缺少官方"拼接全期"口径 → 跨度限制已取消

- 现象：规则要求总跨度 > 5 年必须分段，但分段之后没有把各段日收益串成全期指标/净值的接口；
  本轮只能自己按日期拼接（`analyze_costs.py --aggregate`）。
- 修复：**取消"总跨度 > 5 年必须分段"的流程约定**——研究期内任意跨度
  （1 个月 ~ 研究期全段 10 年）都可以单次回测，不再需要任何拼接接口。
  - 事实核对：后端从未存在跨度上限或强制分段校验（`create_backtest` 只校验
    `start <= end` 与研究期/验证期边界，交易日由行情可用区间自然收敛），
    该限制只写在文档与 E 节流程约定里，因此修复是"改写约定 + 锁定行为 + 提示文案"；
  - CLI `backtest run --start` 帮助文本与前端"回测区间"提示明确"任意跨度均可，无需分段"；
    长区间的阶段视角由既有分年度绩效与三段一致性给出；
  - 研究/验证期边界规则**未放宽**：研究类回测仍不得越过研究期末端（2025-12-31），
    跨界需显式 `purpose=validation`（任意跨度 ≠ 任意用途）。
- 验证：`tests/unit/test_backtest_span.py`（1 个月 / 2 年 / 3 年 / 10 年均可创建且只建一条记录；
  越界仍拒绝）。现场实测：`mainline_rs_rotation_v8` 以
  `--start 2016-01-01 --end 2025-12-31`（研究期全段 10 年）**单次跑通**，
  返回 2016~2025 共 10 个自然年的分年度绩效，全程未分段；实测单次 10 年回测
  （2431 个交易日、21 个标的）耗时约 5 分钟，独占回测 lane，可用 `queue stats` 观测。

### C-5 [P2] 删除回测记录会留下悬挂引用

- 现象：用户清空 `backtest_run` 后，`robustness_run.variants[].backtest_ids`、

  日结果/指数结果孤儿行 0 条。

  - 迁移 `0048_backtest_reference_integrity`：先把结构性悬挂引用清理干净

    `backtest_daily_result` / `backtest_index_result` / `backtest_comparison`

    `strategy_lifecycle.{research,validation}_backtest_id` → `ON DELETE SET NULL`；
  - JSONB 引用（稳健性变体窗口、优化折窗口）无法加外键，改为**可检测 + 可标记 + 可清理**：
    `GET /backtests/orphans` / `cli backtest orphans` 审计悬挂引用；

  - `robustness collect` 不再把"已删除的回测"当成"仍在排队"——单独计入

  - 受控删除：`DELETE /backtests/{id}?force=`、`cli backtest delete <id> [--force]`，
    运行中的回测必须先取消；存在 JSONB 引用时默认拒绝（409）并列出持有者；
  - 可见性：`RobustnessDetail.missing_backtest_ids`、`optimization show` 的
    `missing_backtest_ids` 与报告中的"⚠ 缺失引用"小节、生命周期页对空回测引用

### D-1 [P1] 缺少"批量变体 → 秒级评估"的官方路径

- 现象：探索性诊断（消融 9 个 + 池扰动 9 个 + 参数 15 个 + 简化 6 个 ≈ 40 个变体 × 5 段）
  在平台上等于 200 条回测，在当前吞吐下需要数小时；本轮只能在研究目录里复刻引擎
  （`v8_local.py`，换手/仓位与平台完全一致、收益差 < 1pp）才把成本压到秒级。
- 根因：(a) 每条变体都要落库（逐日结果 + 逐指数结果，单条 2 年 ≈ 5 万行）；
  (b) 同一窗口的行情加载与因子预计算在每个变体上重复一遍。
- 修复：新增 `research batch` 命令组与 `ResearchBatchService`，
  **复用与平台完全相同的执行路径**（`_run_backtest_loop(persist=False)`），
  只关闭结果落库与状态提交，并按窗口共享行情快照与因子预计算：
  - `cli research batch --strategy <基线> --variants variants.json --windows 5 [--cost-bps] [--cost-ladder]`；
  - 变体文件支持完整 `config` 或 `patch`（点号 / 列表下标路径，如
    `filters.rules[1].value`），patch 的路径不存在会直接报错而不是静默跳过；
  - 输出逐窗口毛口径 + 净口径指标、多档成本并列、`vs_baseline`（Δ净年化 / Δ净夏普 /
    劣化窗口占比），以及固定口径指纹（执行模型 / 数据质量 / 基准 / 日历来源 /
    换手口径 / 成本 / 区间）；
  - **不落库即不可审计**：输出里 `caliber.persisted=false`，验收仍必须走 `backtest run`。
- 为什么不是"再写一个引擎"：C-1（周末近似日历）与 B16（warn/strict 候选池分叉）都是
  "两套实现、两套结果"造成的；批量路径与平台共用同一条代码路径，回归测试
  `test_metrics_match_persisted_path` 锁定"落库与不落库两条路径的逐日收益、换手、
  仓位完全一致"。

### D-2 [P1] `robustness scan` 的默认规模与实际吞吐不匹配

- 现象：默认 `--max-knobs 30` × `--windows 4` = 136 条回测；更糟的是截断按**路径字母序**，
  默认 30 档时 `timing.thresholds.*`（最可疑的拟合参数）永远排在最后被截掉。
- 修复：
  - 截断顺序改为**业务重要性**（`_KNOB_PRIORITY`）：择时阈值 → 过滤阈值 → 评分权重 →
    风险 / 仓位 → 调仓；同优先级内仍按路径排序，保证可复现；
  - 支持**关键旋钮清单**：`--knobs timing.thresholds.offensive_score,filters.rules[1].value`
    或 `--knobs-file knobs.json`，只扫清单内字段；清单里的路径不存在时直接报错；
  - 新增**轻量体检预设** `--preset quick`（2 窗口 / 8 旋钮）与 `--preset standard`
    （4 / 30，与旧默认一致）；显式 `--windows/--max-knobs` 优先于预设；
  - 扫描口径随批次落库（`robustness_run.scan_params`：preset / knobs / windows），
    前端批次详情与 `robustness show` 都能看到"这批到底扫了什么"；
  - `--preset quick` 已写进 strategy-optimizer 的技能流程与验收清单（第 6 项）。

### D-3 [P2] 稳健性结果没有进入前端

- 现象：`robustness` 只有 CLI + 只读 API，页面上看不到 PBO/DSR/邻域结论，

  - 批次列表（类型 / 状态 / 试验数 / 窗口 / 创建时间），运行中的批次可直接取消；
  - 批次详情：扫描口径、覆盖率（部分汇总会显式标注"结论仅供参考"）、

### D-4 [P2] 稳健性变体策略的清理没有元数据支撑

- 现象：一次 scan 会批量创建 `<base>__rbXXXX_*` 形式的 draft 策略（本轮 33 个），

  - 新增 `cli strategy prune-variants --batch <批次ID>`：
    默认**预演**（`--apply` 才真删）；变体仍被回测引用时跳过并列出引用，

### D-5 [P2] 验证期留痕只覆盖回测，不覆盖"研究者的眼睛"

- 现象：v8 的历史版本说明显示 v1.4~v1.6 都在 2010-2026 全区间（含 2026 验证期）上选参数，

- 修复：
  - `strategy_config` 增加 `validation_consumed_at` / `validation_consumed_note`

## E. 本轮实际操作中值得保留的做法

1. **先对齐再分析**：本地复现必须先与平台逐段对齐（换手/仓位完全一致、收益差 < 1pp）
   才允许用来下结论；对齐过程本身就是发现 C-1 的方式。
2. **分段是可选的分析视角**（C-4 后不再是流程强制）：研究期内任意跨度都可单次回测；
   想逐段观察时，按自然年/等分段看分年度绩效与三段一致性即可，不需要拼接接口。
3. **成本四档并列**：毛 / 10bp / 20bp / 30bp / 50bp 一起看，换手 13 倍的策略只看毛口径会得出
   相反结论；现在这四档在回测详情里直接并列（`stability.cost_ladder`，C-3）。
4. **区分"探索"与"验收"**：探索用本地引擎（秒级、可跑几十个变体），验收用平台回测
   （正式口径、落库可审计）。
5. **同步 CLI 作为队列的旁路**：队列积压时用 `backtest run`（默认同步）绕开队列，
   单条 17 秒即可拿到正式口径结果。
